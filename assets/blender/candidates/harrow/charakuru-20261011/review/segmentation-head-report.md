# 頭部分割前後の限定検証

Blender 5.2.1をfactory-startup・disable-autoexecで実行。原FBX・アップロードGLB・分割FBXを読み取り比較し、原本は変更していない。数値全文と対象SHA256は `segmentation-head-comparison.json`。

## 判定

**アップロードGLBから分割FBXへの面構成保持を確認した。** 分割FBXに90度回転を追加する必要はない。Blender読込後の座標ではX/Y/Zすべて同方向で、鏡映も不要。

分割FBX位置をGLBへ合わせる式は `q = (p - Cseg) * 0.9995145783841468 + Cglb`。

- Cseg = (0, 0.00000002980232239, 0.49805063009262085)
- Cglb = (0, 0.00000002980232239, 0.497802734375)

補正後の双方向最近傍距離は最大0.0000336913、RMS約0.00001067（全幅約1に対し最大0.00337%）。最近傍の元頂点へ対応付けした三角形を座標集合として比較すると、**51,637面すべて一致、追加0・欠落0**。頂点対応で使われる位置数も元と同じ26,484。この誤差範囲で形状と面接続を保持している。生の浮動小数点座標の完全同一ではない。

## 頂点数

|対象|メッシュ|読込頂点|ポリゴン|三角形|
|---|---:|---:|---:|---:|
|元head4b05 FBX|1|26,484|29,501|51,651|
|upload head.glb|1|27,236|51,637|51,637|
|分割head.fbx|104|26,747|51,637|51,637|

元FBX→upload GLBの頂点位置は双方向距離0、位置の重複を除くと双方26,484。GLBの増加752頂点は同位置の重複として実測できた。分割FBXは誤差許容の最近傍対応後26,484位置となるが、生の位置は小さな差を含む。分割に伴う頂点の重複・近似座標変更があることまでは実測できる。

**Tripo UIの27,806頂点という表示と、FBX読込26,747頂点の差の原因は未確認。** UIの集計対象・書出し/インポート処理の定義を確認していないため、UVや法線の分割が原因とは断定しない。面構成の一致はこのUI数値差と独立して確認した。

元FBXをBlenderで三角化すると51,651面、upload GLBは51,637面で、元FBXとの三角形集合は27,742面のみ一致する。全頂点位置は完全保持されるが、四角形/多角形の三角分割方法等による差があるため、元FBX→GLBの全サーフェスが数学的に完全同一とは主張しない。この限定検証は分割工程の追加破損・軸変更の有無を主に判定した。

検証スクリプト `segmentation-head-compare.py`、実行ログ `segmentation-head-compare.log`。最終実行exit 0。レンダーや材質適合、リグ、ゲーム統合の合格を意味しない。

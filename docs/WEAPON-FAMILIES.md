# 武器系統と派生（6系統・12丁）

## 何が変わったか

武器は3丁（ライフル / ショットガン / ロケット）から **6系統・12丁** になった。各系統は2丁で構成する。

| 系統 | 1丁目 | 2丁目 | 系統の性格 |
|---|---|---|---|
| ライフル | AR-9 リーフ | **SMG-3 ワスプ** | 連射。中距離 |
| ショットガン | SG-4 ブレイカー | **SG-7 スパイク**（スラッグ） | 標準で最大3体貫通 |
| ロケット | RL-2 コメット | **RL-9 メテオ**（重ロケット） | 直進する弾体と爆風 |
| **スナイパー** | **SR-1 ソーン** | **LZ-2 グリム**（レーザー） | 長距離。拡散・距離減衰なし |
| **グレネード** | **GL-6 ホロウ** | **ST-3 リンバー**（粘着） | 山なり弾道と爆風 |
| **特殊** | **KB-6 ケストレル**（反動射出器） | **MD-4 ブルーム**（支援回復銃） | 道具枠 |

### スナイパー系統の中の使い分け

同じ遠距離枠に、**狙って1体を撃ち抜く** SR-1 と、**当て続けて列を薙ぎ払う** LZ-2 を並べた。

| | SR-1 ソーン | LZ-2 グリム |
|---|---|---|
| 1発 | 165 | 8 |
| 連射間隔 | 1.05秒 | **0.045秒**（連続照射） |
| 射程 | **140m** | 95m |
| 貫通 | 1体 | **3体** |
| スコープ倍率 | **2.4倍** | 1.6倍（当て続ける前提で控えめ） |
| 持続DPS | 114 | 114 |

**持続DPSは意図的にほぼ同値にしてある。** 強さではなく形で選ばせるのが狙いで、単発火力・射程・倍率を取るか、貫通と継続を取るかの差になる。

### 特殊枠は「機構」ではなく「役割」

特殊枠は5つの射撃系統のどれにも属さない道具を入れる場所で、**2丁に固定されていない**。`FAMILY_KINDS` はテーブルから自動生成され、ドロップは系統→武器の2段抽選なので、ここに何丁足しても**他系統の出現率は 1/6 のまま**変わらない。

## 設計：`kind` と `family` を分ける

`Kind` は武器1丁、`Family` はその武器の機構。`WEAPONS[kind].family` で引く（`familyOf()`）。

戦闘コードにあった `weapon.kind === "rocket"` / `=== "shotgun"` の直書き分岐は、すべて **テーブルの属性** に置き換えた。

| 属性 | 意味 |
|---|---|
| `family` | 機構の所属。SE・武器モデル・被弾エフェクト・兵士の構えはこれで引く |
| `falloff` | 距離減衰の曲線を `"rifle" / "shotgun" / "smg" / "none"` から選ぶ |
| `pierce` | 標準で貫通する体数（`1` か `3`） |
| `speed` | 指定すると hitscan ではなく弾体を発射する |
| `gravity` | 弾体を落下させる。共通の弾体物理に元からあった項目 |
| `zoom` | スコープ倍率。未指定は従来どおり2倍 |
| `recoil` | 射撃時に**自分**を後方へ運ぶ距離（m） |
| `heal` | 射線の走査先を敵から味方へ切り替える |

弾体（`Projectile`）にも発射時の `radius` と `family` を持たせる。爆発処理は弾がすでに飛んでいる間に武器を持ち替えられても矛盾しないよう、`chain` と同じく**発射時点の値**を使う。

モデルの解決は `modelOf(kind)` が担う。GLBは元の3丁分（`rifle` / `shotgun` / `rocket` × 5グレード）しか存在しないので、全kindはこの3つのいずれかへ解決される。**familyとは一致しない**——反動射出器は特殊系統だがショットガンの形で持つ。

`Event.weapon` は **kind ではなく family** を載せる。これにより音響・描画・ヒットエフェクトの既存分岐が一切増えない。

### KB-6 ケストレル（反動射出器）

至近距離へ散弾5発を撃ち込むと同時に、`recoil: 9` の分だけ自分を後方へ運ぶ。移動には **ショットガンの `repel` が敵を押すのと同じ `move()`** を使う。`move()` は距離を0.2m刻みに分割して壁と床を毎回見るので、壁抜けも落下も起きない。

**反動は水平成分のみ**（`yaw` だけを使い `pitch` を無視する）。上下成分を入れると、上を向いて撃った瞬間に地面へ叩きつけられたり空へ飛んだりするため。

特殊効果「撃退散弾」を積める唯一の非ショットガン武器で、押し返しと自分の離脱を同時に行える。

### MD-4 ブルーム（支援回復銃）

`fire()` が敵ではなく `w.players` を走査する専用経路（`healShot`）へ分岐する。敵向けのエイムアシストより**手前**で分岐するので、味方を狙っているのに敵へ吸い付く事故が起きない。

**単発ではなく散弾7発。** 細い1本の線を、動いている味方に、スマホの視点操作で当てるのは現実的でない。

ただし**円錐を広げすぎると遠距離でかえって当たらなくなる**（的より散弾の広がりが大きくなり、周りに散る）。実際に拡散0.085で試したところ40m先で1発も当たらなかったため、**拡散は0.05に抑え、代わりに味方の判定半径を1.8mと太くした**（通常の射撃判定より広い）。狙いのズレは「回復量が減る」で払わせ、「空振り」にはしない。

- 射程45m。まっすぐ狙えば40m先でも7発中6発が当たる
- `damage` の数値が**散弾1発あたりの回復量**（全弾命中で7倍）
- レア度とバリアンスがそのまま回復量に効くので、進行システム側に第2の経路を作らずに済む
- ダウン中（HP0）の味方は対象外。蘇生は従来どおり
- 回復は `maxHp(w)` で頭打ち
- 特殊効果「貫通」を積むと一直線の味方を最大3人まとめて回復
- 回復量は**味方ごとに合算して1回だけ報告**する。散弾7発で数字が7個飛ばないようにするため

**フィードバックを機構と同時に入れてある。** 2026-09-06 の「味方が救助できない」バグは、処理が正しいのに救助側の画面が無反応だったのが真因だった。回復銃は同じ形をしているので：

- 回復量を緑の `+38` として**撃った本人に必ず表示**する。ダメージ数字の表示設定が「オフ」でも回復だけは出す
- 味方が満タンで回復量0でも、**射撃イベントと効果音は必ず出す**。「当たったが何も起きなかった」と「壊れている」を区別できるようにするため

## セーブ互換

- **既存3丁の数値は1つも変えていない**（`tests/weapon-families.test.ts` がリテラルで固定）
- 新規セーブの初期装備も従来どおり3丁のみ。新系統は入手して増やす
- 旧セーブに新 `kind` は存在しないので、そのまま読める
- 効果の可否判定のうち `repel` と `chain` は「その武器の抽選プールに入っているか」を見る形にした。`pierce` だけは family 判定のまま残してある（旧セーブのショットガン+貫通を読めなくしないため）

⚠️ **逆方向は非互換。** 新 `kind` を含むセーブを旧クライアントで読むと `validWeapon` が弾く。公開後に巻き戻すと、その武器は失われる。

## ドロップ率

`rollWeapon` / `loot` は **2段抽選**。まず6系統を均等に引き、次にその系統内から引く。

⚠️ **当初この文書に「12種均等より希釈が半分で済む」と書いていたが、これは誤りだった**（2026-09-22の独立監査で指摘）。各系統が2丁の現状では `1/6 × 1/2 = 1/12` で、12種均等とまったく同じ確率になる。特定の1丁を狙う周回効率は、2段抽選にしても一切改善しない。

2段抽選に意味があるのは**系統単位で見たとき**だけ。「ライフル系が出る確率」は系統数だけで決まる 1/6 に固定され、**その系統に何丁足しても他系統の出現率が動かない**。特殊枠に武器を増やしてもライフルの出現率が下がらないのはこのためで、確率の希釈そのものを減らす効果はない。

`tests/game.test.ts` が10万件のドロップで各系統の比率が 1/6 ± 2% に収まることを検証する。

## 武器庫の上限

`CAPACITY.perKind = 16` は元から「系統ごと」と文書化されていたが、実装は `kind` 単位だった。系統が6つになると 12 × 16 = 192 で全体上限160を超えるため、**実装を文書どおり family 単位に揃えた**（6 × 16 = 96）。

対象: `progression-save.ts`（検証・`bank`）、`save.ts`（`trimToKindCap`・報酬受領・保留の引き上げ）、`daily-rewards.ts`。

## 独立監査で見つかった5件（2026-09-22に修正）

自己検証では1件も見つけられなかった。記録として残す。

### F1（P1）新武器のモデルが読めず出撃準備が落ちる

`progression-weapons.ts` と `weapon-sharing.ts` が `${kind}_${rarity}.glb` を要求していた。GLBは元の3丁分しか無いので、**新武器を装備した時点で読込が例外になり、協力では他の参加者の準備まで巻き込んで失敗する**。実装時に `standard-trooper.ts` の武器モデルだけを見て、別ファイルのローダーの存在に気づいていなかった。`modelOf()` で解決するよう修正。

### F2（P2）爆発の半径とfamilyが固定

弾体に半径を持たせておらず、爆発処理が `radius: 6.5` / `weapon: "rocket"` 直書きだった。**メテオ11m・ホロウ5m・リンバー4.2mが1つも効いていなかった**。減衰式 `1 - d / 9` も半径6.5前提で、半径だけ広げると9m超で負のダメージになる。弾体に `radius` / `family` を持たせ、減衰の到達距離を半径に比例させて修正（元のロケットは `(6.5 × 9) / 6.5 = 9` で数値が完全に一致する）。

### F3（P2）反動射出器の撃退散弾が発動しない

抽選プールでは `kick` に `repel` を許可しておきながら、発動側に `family === "shotgun"` が残っていた。自分で書いた2箇所の矛盾。判定をプール参照へ統一。

### F4（P2）同系統2丁持ちで着弾音の判定対象を取り違える

`weapons.find(v => familyOf(v.kind) === e.weapon)` が**同じ系統の先頭の銃**を拾う。ライフルとSMGを両方積むと、SMGで撃ってもライフルの射程65mで判定され、鳴るはずのない着弾音が鳴る（逆も起きる）。

クライアントが武器を特定しようとしたのが誤りだった。**権威側が「弾が途中で止まったか」を `stopped` としてイベントに載せる**形に変更し、クライアントは武器を引かなくなった。同じkindを2丁積んだ場合の曖昧さも消える。

### F5（P2）連射がサーバーのtickで頭打ちになる

サーバーは50ms刻みで、1tickにつき `fire()` を最大1回しか呼ばない。**0.045秒間隔のレーザーは毎秒20発で頭打ちになり、連射バリアンスが一切効かなかった。**

さらにレーザーだけの問題ではなかった。発射間隔は `interval / (1.15^グレード × (1 + 連射バリアンス))` なので、**高グレードのSMG（0.07秒→0.033秒）も同じ上限に刺さる**。

`p.cool` を代入ではなく加算にし、トリガーを引いている間は1tick分まで負の残りを保持して、1tickに複数発撃てるようにした。

⚠️ **既存武器への影響。** この修正で、実効間隔が50msの倍数でない武器はすべて実際の連射速度が上がる。**ライフルは 6.7発/秒 → 7.7発/秒（約+15%）**。従来は武器画面に「連射 7.7」と表示しながら 6.7発しか撃っていなかったので、表示に実装を合わせた形。`tests/game.test.ts` の連射テストは旧来の量子化された値を期待値に固定していたため、仕様準拠の値へ更新した。

**「ショットガンとロケットは基礎値が50msの倍数だから変化なし」と当初書いたが、これは不十分だった**（2026-09-22の再監査で指摘）。実効間隔は `基礎間隔 / (1.15^グレード × (1 + 連射バリアンス))` なので、**グレードやバリアンスが付いた時点で倍数から外れ、同じように速くなる**。独立監査側の計測では、LR・バリアンス0のショットガンが装填込み10秒で 19発 → 21発 になっている。

つまりこの変更は特定の武器ではなく、**全12丁の全グレード・全バリアンスに及ぶ**。`tests/weapon-families.test.ts` が 12丁 × 3グレード × 2バリアンス ＝ 72通りで、実発射数が定義どおり（±1発、高連射帯は±2%）に収まることを検証する。

## 再監査で見つかった1件（2026-09-22に修正）

F1〜F5の修正は「直接原因の解消を確認」と判定されたが、**その修正が生んだ二次被害**を指摘された。

### R1（P2）イベント保持上限にイベント増加が追従せず、送信前に通知が消える

`event()` は80件を超えると**送信済みかどうかを問わず先頭を削除**する。`prepareState()` は残っているものしか送れないため、削除された通知は二度と届かない。

F2（爆発が広くなり命中する敵が増えた）とF5（発射数が増えた）で、1回の処理が生むイベント数が跳ね上がった結果：

| 再現 | 内訳 | 結果 |
|---|---|---|
| 4人が高連射レーザー（100ms） | 発生83件 / 送信80件 | 先頭3件の**命中通知が消失** |
| メテオが40体を巻き込む | 爆発1＋命中40＋撃破40＝81件 | 先頭の **`burst` が消え、爆発音も演出も出ない** |

ダメージ自体は正しく入る。**消えるのは表示と音だけ**——処理は正しいのに画面が応答しない、という救助バグと同じ形をしている。

送信サイズは14,315バイトで上限65,536の範囲内だったので、**これは通信量ではなく保持数の問題**。

**修正方針。** 保持数を無制限に増やすのは危険（65,536バイト超過は切断になる）。そこで **溢れたときに捨てるものを重要度で選ぶ** 形にした。

- 上限を `LIMITS.events = 160` として明示
- 溢れたら**最も古い `hit` から捨てる**。`hit` は大量発生する上、失っても損失はダメージ数字1個
- `shot` / `burst` / `kill` / `down` / `revive` / `heal` は**必ず残す**。どれも音か演出を駆動しており、他に届く経路がない

満杯のバッファ（160件）＋敵40体＋長いフィールド値での送信サイズは **29,210バイト**（上限の45%）。テストでは余裕を含めた45,000バイトを閾値に固定してある。

## 再々監査で見つかった1件（2026-09-23に修正）

R1の修正で元の2条件（レーザー83件・メテオ81件）は全件送信されるようになったが、**削除方式そのものが新しい欠陥を生んでいた**。

### R1-R（P2）送信済みイベントが容量を占め続け、新しい命中通知が消える

`prepareState()` は送信対象を選ぶだけで、**送信済みのイベントをバッファから消さない**。160件が送信済みの `shot` で埋まると、次に来た `hit` は「最も古い `hit`」として**追加された直後の自分自身が削除される**。以後の `hit` も同じ。ライフルを160発空撃ちした後に敵へ当てると、HPは減るのにダメージ数字も命中音も出ない（監査側実測。命中パケットは1,433バイトで、瞬間的な大量発生も送信サイズ超過もなしに起きる）。

**「`hit` を捨てても損失はダメージ数字1個」という前提も誤りだった。** ライフル系の対敵命中音は `hit` から作られ、`shot` 側の代替着弾音は抑制されている。`hit` を捨てれば命中音も消える。

また「重要イベントは**必ず**残す」も実装と一致していなかった（`hit` が無ければ重要イベントでも先頭を消す）。

**修正。** 容量制御の対象を**未配送区間だけ**にした。

- `retireEvents(w, delivered)` を追加。**配送済みのイベントをバッファから退役**させる
  - 協力：Workerの `broadcast()` が送信後に `sentEvent` まで退役
  - ソロ（`main.ts` / `playtest-app.ts` / `training-app.ts`）：**描画と音の両方が取り込んだ位置の小さい方**まで退役。どちらかが取り込んでいなければ残る（例：登場演出で描画が止まっている間は退役しない）。取り込み位置は run ごとで、別runの値は0として扱う
- 溢れたときに捨てるのは「**同じ射手の、より新しい `hit` が残っている `hit`**」の最も古いもの。命中音は射手ごとのキーで75ms内に1回へまとめられるので、新しい方が音を鳴らす＝**失うのはダメージ数字1個だけで音は失わない**
- 冗長な `hit` が1件も無いのに溢れる（＝1回の配送間隔に160件を超える、それぞれ別の音・演出を持つイベント）場合だけ、最古のものを捨てる。65,536バイト超過は切断＝全損なので、上限は守る。**「必ず残す」とは言わない**：この場合は重要イベントも消えうる

サイズテストは本番と同じ形のメタデータを渡し、`JSON.parse()` 成功と160件の搭載を確認する形に直した（空のメタデータではJSONとして不正な文字列でもバイト数検査だけ通っていた）。実測 **29,331バイト**。

## 未検証・限界

- **実際にプレイしていない。** 手触り、難易度曲線、戦闘のテンポ、12丁の体感バランスは未評価。上のDPS表は算術であって遊んだ結果ではない
- **実スマホ未検証。** 反動射出器の移動距離が実機の視点操作で扱えるか、レーザーを95m先の的に当て続けられるかは未確認
- **実協力通信での検証が未了。** 回復銃は4人協力でこそ意味を持つが、権威サーバー経由の複数人同時回復は単体テスト止まり
- 新系統の3Dモデル・発砲音は**既存アセットの流用**。スナイパー/特殊はライフル、グレネードはロケットの見た目と音を使う。回復音は蘇生音の流用
- レーザーは「連射間隔0.045秒の hitscan」であって、専用の連続ビーム描画や過熱処理を新規実装したものではない
- 反動射出器の移動は水平のみ。段差や崖を跳び越える用途では、落下の扱いが `move()` の既定挙動に従う

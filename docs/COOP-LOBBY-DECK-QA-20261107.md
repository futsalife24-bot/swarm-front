# 協力入室と出撃前カードデッキ編成（2026-11-07）

## 変更

- ホストの部屋作成とゲストの入室は、どちらも協力ロビーへ直接入る。入室だけで準備完了にしない。
- 協力の生存戦では、ロビーから「カードデッキ編成」を開く。既存の生存カード画面を使い、取得条件、融合説明、抽選対象と除外枠を維持する。武器選択は表示しない。
- 「保存して準備完了」で既存の除外保存を実行し、デッキ・再接続用デッキ・成長計画を通信へ渡す。保存に失敗した場合は編集画面を維持し、準備完了にしない。
- 編集破棄は既存の確認ダイアログを使う。戻るだけでは準備完了にしない。設定へ移る時も未保存変更の確認を通す。
- 入室直後や編集途中は重い戦場準備を開始しない。保存後に開始し、準備中の再編集を古い非同期処理が上書きしない。
- 画面レイアウトは既存の Claude デザイン担当の差分を取り込んだ。ソロ、防衛、デイリーは既存の準備画面を維持する。

## 確認結果

検証対象はこの作業ブランチのローカル版。既存のローカル Worker と隔離した Chrome のホスト・ゲストを使い、通信をモックに置き換えていない。

- `npm run typecheck`：client / worker とも成功。
- `vitest.front.config.ts` の `front-decks`、`front-survival-progression`、`front-network-opening`、`front-title-entry`：4ファイル・15テスト成功。
- `node scripts/check-front-coop-deck.mjs`：最終実行の8確認すべて成功。
  - ホストとゲストの初期画面がロビー、双方未準備。
  - 未保存の除外編集とキャンセルが、保存済みデッキを変更しない。
  - 既存の除外上限2枚を超えられない。
  - 保存失敗時は準備完了にならず、正常保存時だけ指定の2枚が除外される。
  - 戦場準備中に再編集しても編集画面を維持し、明示的な再準備が必要。
  - 2人の準備完了後、出撃できるのはホストだけ。
  - 実際に2人の生存戦の初期カード選択へ到達。
  - 権威サーバーのスナップショットで、ホスト23枚（衝撃核・徹甲弾を除外）、ゲスト25枚、プレイヤー2人を照合。
- 844×390、640×360、568×320 の実画面で、カード編成と保存・戻る・設定操作が画面内に収まる。568幅でも再抽選数が読める。ページの横・縦はみ出しなし。ページ例外なし。
- `git diff --check`：成功。

## 確認範囲と引継ぎ

- 初回の戦場準備待ちは180秒でタイムアウトした。診断を加えた再実行と、最後の再編集ガードを含む実行では2人出撃まで成功した。端末の描画準備時間について恒常的な高速化を保証するものではない。
- 追加で実行した既存 `front-campaign.test.ts` の1件は、取得カード数の期待値22と実値25の差で失敗した。対象のテストと関連する `front-campaign.ts` / `front-progression.ts` は基準 `ac14198` から未変更。全テスト成功とはしていない。
- ソロ・防衛・デイリーの全戦闘を今回網羅していない。既存画面へ分岐する処理を維持し、関連する型・単体テストで確認した。
- 本番ビルド、ほかのバディ・3桁部屋ID・報酬長押しの差分との統合、main 反映、既存公開先への配信確認は統合担当へ引き継ぐ。本タスク単独では公開していない。
- Claude のレイアウト原本は `docs/COOP-DECK-DESIGN-20261107.md`。元の画像ファイルは正規取得処理が Windows のメタデータ処理で失敗したため、原画像を取得・確認したとは扱っていない。

## ローカル再検証

既存の依存とローカルサーバーを使い、`SWARM_DECK_ORIGIN`（既定5194）と `SWARM_DECK_ENDPOINT`（既定8814）に127.0.0.1を指定する。検証器はローカル専用で、既存の検証用ファイルを `SWARM_TEST_VARS_PATH` から読み、キー値をログや証拠へ記録しない。失敗時は画面状態と限定した通信状態だけを `dist-validation/coop-lobby-deck` へ保存する。既存の個人ブラウザー保存や本番セーブは使用しない。

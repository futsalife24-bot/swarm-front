# Swarm Frontの監査・公開

## 固定する経路

- 2026-09-16ユーザー指示。監査は **Codexアプリ内ブラウザ（iab）→通常の新規Chat→監査ZIPを直接添付→独立判定→指摘修正・同じChatで再監査→main反映→公開確認** に固定する。
- 最初から `cua.createBrowserTab("iab", "https://chatgpt.com/", { visible: false })` を使う。既存の同タスクの監査Chatがある場合だけそのタブ/URLを再利用する。初回はcua_replの初期化規則に従う。
- Chrome拡張版・OSのネイティブ操作・Work・Codexサブエージェントへ勝手に切り替えない。今回の成功経路はiabの標準filechooser。Chromeの「ファイルURLアクセス」変更やPC操作をユーザーに求めない。
- iabで障害が発生したら、現在の画面と公式のブラウザツール手順を確認して最小限の復旧を試す。別経路への無断変更やセキュリティ制限の回避はしない。

## 対象と資料

1. 正規リポジトリ `game/` のAGENTS、WORKFLOW、STATE先頭と実Gitを照合。PR、base、監査対象の完全SHA、未コミット差分、継続承認の範囲を確定する。
2. 実装・必要な自己検証を終えcommit/push。対象SHAの実差分、必要ソースと依存、検証手順・結果、UI証拠をZIPにする。GLB/Blender/比較動画などは変更の監査に必要な場合に含める。無関係な個人情報・秘密情報・依存キャッシュは含めない。
3. 添付が主証拠。非公開PRのリンクだけで監査側が必要ファイルを取得できる前提にしない。資料名とSHA対応、自己検証と未確認範囲を依頼本文に明記する。
4. 通常Chat（Workではない）を画面で確認。`file-uploads`のツール資料を読み、filechooserを待ち受けてから「写真やファイルを追加」を押し、絶対パスで添付する。添付名とアップロード完了を確認して依頼を送信する。

## 監査と承認

- 合格/要修正、対象SHA、必須指摘の重要度・箇所・再現条件、任意指摘、監査側の検証限界を求める。実装担当の自己レビューを独立監査の代用にしない。
- ユーザーは監査依頼・必要修正/再監査・合格後の通常merge/既存Worker公開まで継続承認済み。同一の承認を取り直さない。ただし、このスキル自体は新たなデータ送信権限を付与しない。現在の会話の送信承認と対象資料・送信先を照合する。
- 自動承認レビューの拒否は回避しない。対象資料・通常Chatという送信先・監査目的を特定して、実際に不足した承認だけをまとめて確認する。
- 送信後の監査Chat URLをSTATEへ保存。回答待ちを未依頼と混同しない。待機中は公開準備を進め、適切な間隔で結果を確認する。未完了の回答から合格を推測しない。
- 必須指摘を修正・検証・commitし、同じ監査Chatへ修正SHAと差分/必要証拠を送る。最終対象の必須指摘なしを確認する。

## mergeから公開まで

1. 最新mainとPRチェック/保護を確認。監査後の変更が記録文書だけなら差分を明示し、実装変更があれば再監査する。管理者バイパスをしない。
2. 通常PR merge。更新履歴の具体的な日本語説明はmerge本文の `Player-Note: ...` に保持する。mainへ同期してmerge後HEADから公開用ビルドを作る。
3. 既存の `wrangler.production.jsonc` に従ってdry-runと既存Worker公開。新規サービス・課金・移行を勝手に追加しない。
4. 公開ソースSHA・Worker Versionを記録。配信ファイルのSHA、health、変更に応じた実ブラウザ確認を行う。ソースmain反映と公開を別々に確認する。
5. 公開記録はcommit/pushしてmainへ反映。ローカルmain/origin/mainの一致とcleanを確認して報告。停止時は対象SHA・PR・監査Chat・資料・具体的な障害・再開条件をSTATE先頭に残す。

# Tripoダウンロードの実体確認と停止判定

2026-10-12本人指示「同じミスはしないように厳格にルール化」。今回の確認済み事象に適用する。保護設定・操作権限・既存監査条件は変更しない。

## 必須判断手順

1. downloadイベントのタイムアウト、`.tmp`等の拡張子、ブラウザ内部ページを閲覧できないことだけで、ダウンロード失敗・保存未完了・本人操作待ち・goal blockedと断定しない。タイムアウトは観測終了、内部ページ拒否はそのページの操作制限として区別する。
2. 通常UIの書き出し対象ID・形式・開始時刻・成功/失敗表示を記録する。対象操作で生じた既知の保存先のファイルだけ調べ、無関係なダウンロードを走査・変更しない。
3. ファイルのサイズ・更新時刻が変わらないことを別時点で確認し、インポート前に形式識別子を読む。FBXならBlenderの実インポートを必須とし、終了コード・メッシュ・頂点/面数を確認する。材質付きFBX書出しがZIP（PK）ならCRC・エントリの安全な相対パス・展開サイズを検査し、内部FBXと画像寸法・SHAを確認する。成功JSONは今回の実行で作成されたものに限る。終了0だけで成功扱いしない。
4. 対象ID・操作時刻・UIの面数等と照合する。対応を確定できないファイルは採用しない。差は記録・調査し、形式検査成功を造形品質・アニメーション品質の合格へ広げない。
5. 明示的なセキュリティ拒否がなく、実ファイル検証に合格した場合は、元ファイルを保持して制作先へ正しい拡張子でコピーする。コピー前後SHA256一致を必須とし、ID・由来・サイズ・ハッシュ・読込結果を記録する。改名だけで完成扱いしない。
6. 明示的な危険判定・OS/ブラウザの保存拒否・アクセス拒否は回避しない。アクセスできた一時ファイルを使って拒否を迂回しない。本人への操作依頼は実際の拒否、認証操作、利用可能な手段で解消できない条件を特定してから行う。未確認の保存ダイアログを原因と断定しない。
7. 既に正常な候補が取得できたら同じ候補を再生成せず、その正本と工程から継続する。タイムアウトだけを理由に有料処理を追加しない。
8. 停止原因が解消したら状態文書・本人対応待ち・記憶を訂正し、元の最終目的まで許可済み作業を再開する。部分作業の成功で元のgoalを完了扱いしない。goal状態変更は公開ツールの契約に従い、再開機能がない場合は事実を伝え、内部DBの編集や未完了goalの完了・再作成で代替しない。

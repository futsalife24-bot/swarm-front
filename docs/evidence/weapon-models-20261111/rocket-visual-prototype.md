# RL-9表示補正の隔離試作（未採用）

実ローカル単独プレイの実Rendererで、飛翔体を初めて描くとき所有者の銃口面を一度だけ記録し、先端の位置を維持して銃口より後ろにある表示部分を進行軸方向へ圧縮した。通信データ・当たり判定・飛翔体状態は試作コード上では変更しない。`view.instance` を観測用に差し替えた隔離試作であり、製品には未反映。

- `report.json`: RL-9の初回描画は武器との辺・面交差0組、兵士表面0組。前回の無補正の別走では武器258組。後端の進行方向投影は銃口面付近、前端は前回別走の値との差約0.002mm。面交差は完全内包や共平面を検出できない。RL-2は今回の初回フレームで縮小処理が発動せず、インスタンス中心と飛翔体状態が約0.002mm以内で一致した。両武器の全フレーム・全条件で不変という意味ではない。
- RL-9の先頭の観測フレームで元の62.3%の長さとなり、次に観測できた約0.1秒後には100%に戻った。その間は未観測で、自然な伸び方を確認したものではない。
- `comparison.png` は現状と試作を別走の通常描画で比較した拡大画像。数値は各走の別途計測であり、画像自体の目視で交差を証明したものではない。

この試作は「初めて見た弾」を発射直後と区別できず、途中参加、遅延や再表示中の既存弾を誤って短くする可能性がある。初回に所有者モデルが未ロードなら以後も補正されず、run変更時のID再利用や保存Mapの解放も処理していない。装備切替・他者の弾・複数弾・通信・実スマホの検証はないため、不採用。

通信契約を変えず、新規観測の「同じ所有者・rocket系統の弾1個と射撃イベント1件」を対応付ける案も、これだけでは安全と証明できない。コード上、弾とイベントのIDは別系列で、Frontの状態送信では容量超過時に古いイベントを省略し、衝突した弾は消える。例えば先の弾Aは残り、そのイベントだけ省略され、後の弾Bは衝突して消え、そのイベントだけ残る組み合わせなら、1対1でも別の発射を対応付ける。送信詰まり中は状態更新が留保される。これはコードから構成した反例であり、実通信で再現したものではない。誤った補正の発動・発生頻度や、位置・方向等を追加した別の判定方式の可否は未検証。参照: `src/shared/game.ts` の弾生成・射撃イベントと弾の衝突処理、`src/shared/state-wire.ts` の容量超過時のイベント省略、`server/state-delivery.ts` の送信制御。

再現は作業worktreeのルートで `node scripts/rocket-visual-series.mjs`。結果と各武器の画像は `dist-validation/rocket-visual-series/` に出力する。保存した今回の結果と比較画像は `rocket-visual-prototype-report.json`、`rocket-visual-prototype.png`。比較画像は別走の静止画をまとめたもので、再現スクリプト自体は集約画像を生成しない。既存の正常なRL-2を含む本番動作を保証しない。

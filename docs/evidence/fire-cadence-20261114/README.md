# 押しっぱなし中の連射間隔のばらつき：原因の段の特定と表示側の修正（2026-11-14）

本人報告（OPPO Find X8）「射撃ボタンを押しっぱなしの最中に弾の間隔がばらつく」「ほんの若干重さも感じた」に対し、1発ごとの時刻を **押下 → 入力採取（50ms周期）→ 送信 → サーバー適用 → サーバー射出 → 端末の受信 → 表示（弾・発射炎）→ 効果音** の全段で対応づける診断を追加し、同じ武器・seed・人数で比較した。基点 `a3c089ca9cd0fd58c26139fd679e2c0ae8dc63ed`、branch `claude/fire-cadence-20261114`。

## 結論

ばらつきは1か所ではなく、**3つの段が重なって**いた。入力の欠落・失効と描画の詰まりは、通常条件では原因ではない。

| 段 | 判定 | 根拠（下表） |
| --- | --- | --- |
| 1. 権威側の50ms刻み | **原因（ソロでも起きる）** | AR-9（130ms）は100/150msの交互、SMG-3（70ms）は50/100msの交互。変動係数 約19%／36%。発数は公称どおり。 |
| 2. 状態配信の10Hzまとめ送り | **原因（協力だけ）** | 協力ではARの届く間隔が100/200msへ広がり、変動係数 19%→36〜52%。SMGは受信の45%（95/210回）に2発が同時に届く。 |
| 3. 効果音のまとめ | **原因（協力の速い武器）** | 同じ受信内の同じ射手・同じ系統の射撃音を1つにまとめる既存処理で、協力SMGは305発中95発（31%）が無音。音は10Hzの拍に揃い、弾の数と合わない。 |
| 4. 回線の揺らぎ | **2を悪化させる** | 片道30ms＋0〜70msの揺らぎで受信の変動係数が49〜90%、1受信に3発の場合も出る。 |
| 5. 入力の欠落・失効（250ms） | **棄却（通常・揺らぎあり）** | 押下中に権威側で射撃が無効だったtickは0〜6件で、失効は0件。端末の送信間隔はp95 57〜65ms。失効が出たのはローカルPCの過負荷でサーバー時計が3秒止まった1試行（27tick）だけ。 |
| 6. 描画の詰まり | **棄却（通常条件）**／密集では一部 | 25msを超えたフレームは通常1〜3/約1900。人工密集では350/2436だが、表示の間隔は受信の間隔とほぼ同じ（受信の段で崩れている）。 |
| 7. 効果音の最短間隔（45ms）での省略 | **ほぼ棄却** | ソロSMGで6/305発のみ。 |

体感（表示・音の均一さ）と公平性（射出数・ダメージ）を分けると、**公平性の問題は見つからなかった**。サーバーの射出数は公称の連射速度どおりで、修正の前後でも同じ（AR 170〜172発、SMG 301〜305発／30秒、装填込み）。崩れていたのは体感の側だけ。

## 修正（実装済み・表示と音だけ）

`src/client/shot-pacer.ts` の `ShotPacer` を製品の `front-app.ts` に組み込んだ。届いたイベントを順番どおりに保持し、**同じ射手の速い主射撃（連射間隔0.4秒未満・単発）**が武器の連射間隔より詰まって届いた分だけ、描画と音へ渡す時刻を遅らせる。

- 権威側の射撃・ダメージ・入力の受理・失効期限・連射速度は**一切変更していない**。DPSは不変。
- 遅らせる上限は160ms。射撃が連射間隔の2.5倍以上途切れたら、次の1発は即時に出す（押した直後の1発目は遅れない）。
- 散弾・遅い武器・カード効果やバディの追加射撃・敵の射撃は対象外。順番を保つので、後続の命中表示が射撃より先に出ることはない。
- 協力で描画より先に次の戦況が届いても、未表示のイベントは失われない（以前は描画前に上書きされた分が欠ける可能性があった）。
- 描画と音にだけ均したイベントを見せ、戦況のイベント配列はその後すぐ元へ戻す。

**代償：自分の連射の表示と音が、受信からの中央値で約38ms（ソロ）／63〜84ms（協力）遅れる。** 最大は約200ms。命中の数字も同じだけ遅れる。押しっぱなしの途中の遅れで、1発目は遅らせない。この遅れが気になる場合は上限 `MAX_DELAY`（160ms）を下げられるが、その分だけ均一さは落ちる。

## 追加した診断（既定はオフ）

設定の「通信の詳細診断」がオンの出撃だけ記録する。オフでは記録用の部品自体を作らない。

- 端末：射撃ボタンの押下・解除の時刻、50ms周期の入力採取と送信の時刻、受信、表示、効果音の結果（再生／同じ受信の別の射撃音へ統合／最短間隔で省略／音声無効）、25msを超えたフレーム。上限付きで、照準・移動・部屋ID・名前は保存しない。
- サーバー：tickごとに、適用した入力番号、射撃の保持・失効・未入力・装填中などの状態、そのtickの射出数と最初のイベント番号、射撃待ち時間、残弾、入力の経過時間。詳細診断を要求した接続にだけ、次の状態へ載せて送り、届いた分を消す（未配信は最大48行）。
- 保存：既存の一時停止画面のボタン。ソロにも「診断を保存」を追加した（以前は協力だけ）。
- 集計：`node scripts/summarize-fire-cadence.mjs --device <保存したJSON> [出力JSON]`

## 本人用の確認手順（約3分）

1. タイトルの「ソロ」→「生存」→ 出撃準備の「設定・操作」を開き、下までスクロールして「通信の詳細診断」を**オン**にする（戦闘中の設定には無い）。
2. 普段どおり協力の部屋で出撃する（ソロでも可）。敵が少ない場面で、**射撃ボタンを15秒ほど押しっぱなし**にする。これを2回。ばらついたと感じたら、その直後が良い。
3. 画面上の一時停止ボタンを押し、「通信診断を保存」（ソロは「診断を保存」）を押す。保存されたJSONを送る。
4. 終わったら同じ設定で「通信の詳細診断」を**オフ**に戻す。

保存されるのは時刻・番号・射撃ボタンを押していたかだけで、照準・移動・部屋・名前は含まない。

## 採用しなかった案と、Codex向けの仕様

- **サーバーの射撃処理を50ms刻みから外す・連射速度や失効期限を変える**：採用しない。射撃の受理ルールの変更で、根拠なく変えない指示に当たる。今回の表示側の修正で、権威側の100/150msは画面上では見えなくなる。
- **状態配信を20Hzへ上げる**（2の根本対策）：未実装。受信のまとめは半分になるが、下りの通信量・DO負荷・無料枠への影響が大きく、今回の範囲を超える。実施する場合の仕様：
  - 変更箇所：`server/worker.ts` の `tick()` 末尾 `if (this.ticks % 2 === 0) this.broadcast();`、`LIMITS.snapshotHz`、状態の流量制御（`server/state-delivery.ts` の未確認2件の枠）。
  - 完了条件：4人・人工混在で、下りpayloadと `server.tickMs`・`clockDroppedMs` が現行の判定表（`docs/evidence/coop-comfort-close-20261114/`）を悪化させない。60KiB予算・分割・差分配信の互換を維持。無料枠の試算を更新。
  - 検証：本ページの `measure-fire-cadence.mjs` 全11条件で受信のcvと1受信2発の割合、`scripts/check-coop-live.mjs` の既存条件、全件テスト。
- **効果音のまとめ処理を外す**：ShotPacerで1発ずつ届くようになり、統合は事実上起きなくなったため（欠落 95→1〜3）、既存の統合処理は残した。散弾の粒をまとめる役割を保つため。

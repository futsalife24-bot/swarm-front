# 後半の操作入力の空白と上り滞留への対応

2026-10-30。先行実装100ad9e、作業開始38cf846。30秒の比較だけでは見えなかった問題を、2分の通常4人戦闘で確認した。最新の作業状態はdocs/STATE.mdと本記録を参照。先行検査の成功を、この問題の解消証拠へ読み替えない。

## 追加で確認した原因

4接続のうち1つを実描画、各方向75ms/131,072B/sの未圧縮payload制限で120秒続けた。状態の送信窓は2件へ収まるが、入力の未ACK上限4件も同じ遅い下りのstateを待つため、後半に実送信の空白が最大700〜740msまで伸びた。サーバーの入力有効期限250msを超え、操作しているのに中立入力へ戻る。強化選択後の猶予から1秒以上過ぎたcombatだけでも、4人に131/161/160/159件のack=0が残った。描画最大50ms・100ms超frameなしの試行でも再現したため、描画停止や強化選択だけでは説明できない。

またstateAckを含むinputを受けた際、サーバーは入力を受理する前にdirty状態を送っていた。実通信回帰で最初に返るinputAck=-1を再現し、順序修正後は同じ入力のseq=777が入り、次tickの移動にも適用されることを確認した。

原本: `live-flow-long-128k/`、送信時刻と猶予を追加した `live-flow-input-trace/`。いずれも `dist-validation/coop-comfort-20261030/` 以下。後者の `input-gaps.json` に30秒区間ごとの空白と猶予外ack=0を集計した。元の先行結果は保持。

## 比較した案

- ACK同梱の順序だけ修正: 古い確認番号を返さなくなるが、下りに同じTCPの待ちが残るため、入力4件だけでは十分な余裕がない。
- 独立した小さいACKを追加: 同じTCP内の先頭待ちを追い越せず、応答の種類だけ増えるため今回は不採用。
- 入力窓16へ固定拡大: 同じ120秒検査で猶予外ack=0は1/0/1/0へ減り、描画を外した3人の実送信最大間隔は約71ms。描画clientの1件は350ms frameと重なる。ただし上りだけ1000B/sに落とすと古い操作が溜まり、操作解除後の受理確認が2.30〜3.41秒へ悪化した。旧4件の診断対照では0.91〜1.03秒。固定16は採用しない。
- 適応的な4/16件: 下りだけ遅い時は16、上りとサーバー処理の待ちが増えている時は4へ絞る候補。20Hz・4096Bの送信buffer制限、サーバー250msの入力期限、35件/秒の受信制限、固定dt・武器性能は維持する。

## 作成時刻での判定は不採用

各入力の実送信時刻と、サーバーがstateを作成した時刻を同じseqで照合する。差には上りとstate作成待ちが含まれ、下りの到着待ちは含まれない。接続内の最小差を保持して時計offsetを相殺し、最小値より150ms超の悪化が2回連続したら窓4へ戻す。75ms以内が3回連続したら16へ戻す。窓変更時に最小値を上方へリセットして、滞留を正常と学習することはしない。初期は16、旧サーバーや作成時刻が欠けた状態では4。真の再接続は観測をやり直す。

この候補は最初の120秒で猶予外ack=0が4人とも0件、送信間隔最大約74msになった。しかし別seedの次の120秒では後半に5〜8件、送信間隔最大833〜967msが再発した。戦況を返すまでに古くなった入力の作成待ちを、上りの悪化と誤認して窓4へ縮小していた。最初の成功だけでこの方式を採用しない。

元ログで最小差+150msを超えるACKは、正常上りでは5/2673件、極端に細い上りでは107/113件。正常側の超過は単発だったため2回連続の条件を設けた。初回から一定の悪い遅延や時計ジャンプを完全に識別する方式ではない。十分な証拠がない状態を実機の快適さの保証には使わない。

## 最終方式: 入力の受信時刻で判定

サーバーが新しいseqの有効な入力を受け取った時刻を、そのseqと一緒に `inputReceivedAt` として返す。stateの作成時刻 `serverNow` は適応判定に使わない。時間が経ってから同じseqを返しても、受信時刻は書き換えない。これにより上りと入力message処理の遅れを観測し、stateの生成待ち・下り配信待ちを分離する。

接続内の最小差と150ms/75ms、2回/3回の条件、初期16件・縮小4件は上記と同じ。時刻が欠ける旧サーバーは4件へ戻す。stateFlow対応の進撃・生存の両方で使い、stateIdを時刻へ読み替えない。サーバーの入力期限や権威判定にはclient時計を使用せず、入力の受理情報は接続内だけに持つ。ユーザーのセーブ形式は変更しない。実通信では同梱ACKの最初の応答にseqと受信時刻が入り、350ms後の同じseqでも受信時刻が変わらないことを検査した。

## 上りを細くした対照

適応版を上り1000B/s・下り16MiB/s・各方向75ms、30秒戦闘/15秒で操作解除として確認した。解除を決めてから最初の解除入力の受理確認まで0.67〜1.00秒で、固定16の2.30〜3.41秒から短縮した。初期の学習前には最大約2.65秒の受理応答があり、4固定の最大約0.96秒を全期間で上回るわけではない。極端に細い上りを快適と判定していない。いずれも別seedで、死亡や敵配置の差も含む。

原本: `live-input-window-16/`、`live-input-window-slow-up/`、`live-input-window-4-slow-up/`、`live-input-adaptive-slow-up/`、`input-release-comparison.json`。4固定対照は同じ製品コードに検査側だけで窓4のoverrideを適用した条件で、旧commit全体を再現した試行ではない。

上記の適応版は作成時刻を使った中間版。入力受信時刻へ変更した最終版の再確認結果は後述する。

## BASTION初使用の準備

中間版120秒では、BASTION初登場時に新しいarmorプログラムが追加され、`getProgramInfoLog`に53.7msを要した。生存でも出現前のロード画面でモデル・halo・弾の予告・火花・閃光を準備する。Worldへ敵を追加せず、通常の個体一覧から分離した非表示のモデルを1つ保持する。火花/閃光の色属性も先に確保し、初被弾時のshader変更を避ける。clearでは隠した準備個体を再利用し、disposeで専用材質を解放する。モデルの見た目・動作・戦闘性能は変更しない。

`live-bastion-warm-adaptive/`では準備約13.3秒、状態復元成功。BASTION初登場でのプログラム追加と50ms超のGL呼び出しを再現しなかった。描画frame最大66.6ms、100ms超0件。ただしこの試行には上記の入力窓の再発があるため、全体の性能合格とは扱わない。以前の別試行で記録された350ms frameの全原因を、この修正だけで説明したとはしない。

## 最終統合検査と限界

入力受信時刻版の関連単体92件、BASTION既存36件・追加5件、client/worker型、同梱ACK/受信待ち/最後の結果/再接続を含む実通信2件は成功。新5件は92件にも含まれる。最初の単体起動は共有node_modulesの一時ファイル書込がsandboxでEPERMとなり、正式な権限手順で再実行して成功。実通信の子担当初回はセッションID8686をportと誤認して接続に失敗し、実際の8793へ直した。単体の初回fixtureでpreparationGenerationが不足した失敗も保持し、製品のguardは緩めていない。

入力受信時刻版の120秒（`live-input-receipt-long/`）は4人とも猶予外ack=0が0件、250ms超の入力送信間隔も0件。最大送信間隔は描画client176ms、通信専用3client71〜102ms。描画frame p95は16.9ms、最大150ms。適用応答の最大約0.8秒は残り、模擬の遅い下りまで無遅延になったとはしない。BASTION出現時の新shader追加・50ms超GL呼出しは0件。

上り1000B/s・下り16MiB/s・各方向75msの最終30秒（`live-input-receipt-slow-up/`）では、15秒で解除を決めてから受理確認まで0.83〜1.06秒。初期を含む受理応答最大は約2.38秒で、極端に細い上りを快適とはしない。死亡したclientもあるため、解除後の人物動作の遅延と同一視しない。通常4人120秒・細い上り30秒ともsource hash前後一致、画面/GL例外・途中切断0。

旧通信の既存6件も成功（対象外7件skip）。回線helperは上り/下りの独立制限を加えたecho10件に成功。[単体・実通信結果](input-validation-results.json)、[helper結果](link-shaper-asymmetric-results.json)。通信制限は未圧縮payloadの診断条件で、実回線TCPの帯域や料金ではない。

150ms frameはgame54.9/crawler49で1回だけ。全期間のrender処理最大57.1ms、pilot最大2.1ms、当該時刻のshader追加0、監視対象の戦闘中50ms超GL呼出し0。通信専用3clientのRAF最大は19ms以内。render単体・pilot単体・新shaderが150msを占めたという証拠はなく、全process共通停止の証拠もない。GC・別callback・ブラウザ/OS/driverのどれかはこのログでは確定できない。

CPU診断を付けた追加120秒（`live-input-receipt-profile/`）ではRAF間隔499.9msを1件記録した。入力をframeで送る検査clientには、この間の送信停止と猶予外ack=0が1件ある。通常連携の回帰が全部0だったと一般化しない。render全最大56.1ms・pilot2ms。profileとWorld受信ログ13点を約±0.1msで照合すると、長間隔の約481ms（96.2%）はidleで、途中の2回のWorld受信処理も実行されている。JavaScript main thread全体が500ms一括停止したという説明とも合わない。RAF/描画の呼出し待ちが中心だが、GPU/compositor/OS/可視性のどれかはCPU profileでは確定できない。

検査用の1秒ごとの`getError`は製品render外で、既存GL監視対象にも入っていない。この呼出しの約53msは上の長間隔終了後にあり、499.9ms本体とは分ける。[CPU集計](cpu-profile-analysis.json)、[再集計script](analyze-cpu-profile.mjs)。時刻の照合残差は約0.1msだが、sampling約1〜2msの位置ずれを見込む推定であり、直接共有timestampの計測ではない。CPU診断を性能改善率の測定として使わず、150ms・350ms・499.9msが同じ原因とも断定しない。原因不明の単発RAF待ちと実機確認は残件とし、根拠のない戦闘・描画コード変更や数値の丸めで隠さない。

各試行の比較は [結果JSON](input-continuity-results.json)、集計は [再集計script](summarize-input-continuity.mjs)。`node docs/evidence/coop-comfort-20261030/summarize-input-continuity.mjs` でローカル原本から再集計できる。通常の120秒は `SWARM_LIVE_SECONDS=120 / SWARM_LIVE_RENDER_CLIENTS=1 / SWARM_LIVE_NETWORK_TIMING=1 / SWARM_LIVE_DIAGNOSTICS=1 / SWARM_LIVE_LINK_LATENCY_MS=75 / SWARM_LIVE_LINK_BYTES_PER_SECOND=131072`。細い上りは30秒、`SWARM_LIVE_UP_BYTES_PER_SECOND=1000 / SWARM_LIVE_LINK_BYTES_PER_SECOND=16777216 / SWARM_LIVE_RELEASE_AFTER=15`。出力先は `SWARM_LIVE_OUTPUT` で毎回別にする。CPU診断だけ `SWARM_LIVE_PROFILE=1` を追加する。

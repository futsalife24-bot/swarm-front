# 遅い接続へ古い戦況を溜めない送信制御

2026-10-30。実装前HEAD `bf30da332b6636bc51cbf935912ea0d323de93e6`。ソースhashと機械集計は [検証結果](state-flow-results.json)。マルチ快適化goalの一部であり、全端末での解消・本番反映は未確認。

## 原因と変更

1画面を実描画し、4人分を通常のWebSocketと操作入力で動かす検査に、各接続・各方向75msと131,072B/sの制限を追加した。サーバーが10Hzで全戦況を送ると、遅い接続に古いsnapshotが並び続ける。修正前には30秒の観測で入力応答の最大が約1.34秒、表示されたゲーム進行が28.85秒になった。サーバーとブラウザはともに実装そのものを使っており、同期をmockにはしていない。

新しい `stateFlow:1` をhelloで交渉し、対応welcomeを受けた接続だけ、受信・検証を終えた状態IDをACKする。サーバーが送信済みとして保持する未ACKの状態は接続あたり最大2件。窓が満杯なら送信を保留し、ACKが来た接続へ最新の完全なWorldを送る。古い状態の中間経過を行列に溜めず、敵や弾の項目を欠落させる代用はしない。

- ACKは通常の入力等へ同梱する。操作がない場合だけ100ms後に単独送信し、単独ACKは最大10Hz。既存の受信35メッセージ/秒制限は維持。
- 実際に送信済みのIDだけ受理し、未送信・負数・重複・不正なACKは窓を開けない。ACKによる追加配信は当該接続だけなので、全員への連鎖配信を起こさない。
- 全分割片のsend成功後だけ送信済みID・装備cache・演出の到達位置を進める。部分送信失敗は成功扱いしない。再入broadcastで新しい状態を送った接続へ、外側の古いsnapshotを後送しない。
- 演出の到達位置を接続ごとに持ち、遅い接続へ未送信の演出を既存の160件上限内で残す。古い演出IDの二重再生は既存client側の判定を維持。
- 戦闘tickが止まった最後の結果もdirtyとして保持し、ACK後に送る。同一WebSocketが休止復帰する場合は有限の窓と位置をattachmentに保持。本当の再接続は新しい窓で再開する。ユーザーの保存形式・World・戦闘ルール・64KiB/256KiBの既存上限は変更しない。
- 非対応の旧接続は従来の経路。全員の窓が満杯なら全Worldの符号化も省略する。通信能力を偽ってACKしないclientは自分の配信だけが止まる。

## 実通信での比較

4接続のうち1つだけRendererとGPU事前準備を使用。残り3つは権威サーバーに通常の入力を送る通信診断client。各30秒、ローカルChrome、空の一時プロファイル、実セーブなし。

| ---------------- | -------------- | ----------- | ------------ | -------------------- |
| 制限あり・変更前 | 28.85秒        | 812〜830ms  | 1323〜1343ms | 16.9 / 33.5ms        |
| 制限あり・変更後 | 29.70〜29.80秒 | 461〜476ms  | 501〜533ms   | 16.8 / 33.4ms        |

制限下の下りqueueのピークは接続全期間で変更前242,730〜277,011B（14〜16メッセージ）、変更後は検証JSONに記録した約34KiB前後。観測した機能エラー、WebGLエラー、途中切断は0。ACKの値は単なるpingではなく、送信入力が戦況へ適用された番号を受信するまでの時間。server受理番号の応答もほぼ同じ傾向だった。

別のseed・敵密度なので、厳密な同一戦況の性能倍率とはしない。75msは片方向、帯域は**圧縮前payload**ごとの模擬制限。両側のpermessage-deflateを無効化した検査で、実回線のTCP帯域や通信料金、スマホ性能とは同一視しない。現行Workerがすでに圧縮を交渉できる根拠は [入力遅延調査](input-latency.md#圧縮の前提) を参照。

## 機能・互換・再接続の確認

以前遅れが再現した同一PCの4画面描画も45秒で再確認した。変更後はゲーム進行44.55秒、適用応答p95 136〜155ms/最大450〜572ms、frame p95 33.3ms/最大67〜100ms、エラー・切断0。以前の45秒→40秒・最大応答4.67秒に比べ、この試行では数秒の滞留を再現しなかった。各回のseed・同一PCの負荷差があるので、単独要因の改善率やスマホ保証にはしない。原本は `live-flow-four-render/`。検査中の並行作業は同一PCの小さい文書編集・読み取りで、別の描画検査やビルドは行っていない。

- 関連単体7ファイル81件成功。うち新しいサーバー窓15件、client受信7件。クライアント・Worker両方の型検査成功。
- 新しい実通信1件: 2状態で止まる遅い接続と旧接続を混在させ、旧接続が更新し続けること、不正ACKで窓が開かないこと、戦闘終了後のACKで最後の敗北結果が届くこと、未ACKの結果を残して再接続しても同じrunの結果が届くことを確認。試験はfixtureで戦闘終了を早め、通常の配信と再接続処理を通す。
- 既存legacy実通信6件成功、対象外7件skip。参加人数、戦況共有・再接続、不正入力/過大送信/洪水拒否、武器性能の端数と報酬・再装備、準備世代、clientロビー操作を確認。
- 実4ブラウザの合成負荷: 96敵・400弾・160オーブを受信描画し、その後1000弾へ拡大。各片64KiB以下で復元、WebGLエラー0。500msのメインスレッド停止から復帰し、1人切断後の再接続でも96敵・1000弾を再取得した。合成密度は通常戦闘の出現保証ではない。

原本は `dist-validation/coop-comfort-20261030/` 以下の `live-link-128k-ready/`（変更前）、`live-link-128k-flow/`（変更後）、`live-flow-direct/`（通常回線）、`browser-flow/`、`state-flow-unit.json`、`state-flow-integration.json`、`legacy-flow/`。sourceBefore/Afterは各ライブ検査で一致。

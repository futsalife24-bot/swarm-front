# 初回ANOMALY表示の停止と出撃前準備

2026-10-30。基点6155983からの追加修正。通常の4人戦闘で見つかった停止を、実ChromeのCPU記録・WebGL呼出し・描画プログラムの比較で切り分けた。独立監査ではない。

## 根拠と変更

- 通常生存60秒の最初の有効検査で、PLEAT初出現時に全4画面が6.37〜6.69秒停止した。敵の受信漏れや画面例外はなく、render CPUの停止と受信gapが一致した。
- 診断では出撃準備後の全バッチがinstanceColorなしだった。最初のPLEATに色を設定すると新しいシェーダーが発生。既存と新しいキーの差はThree.js 0.185.1のinstancingColor bitに一致し、client 0の7.73秒停止中7.63秒はgetProgramInfoLogだった。全停止を色属性だけの原因とはしない。
- HoundMotionBatchの色属性を白で事前確保した。初出現時も同じ属性を更新する。未使用スロットは白のまま、色・姿勢・判定を変更しない。
- EnemySpawnEffectsの煙・輪・破片には戦闘中に初生成される別シェーダーがあった。非表示の代表素材を保持し、事前コンパイル対象へ追加。実際の各演出は独立した色・透明度の素材を使い、演出終了で解放しても準備済みプログラムを失わない。
- compileAsync後にも初使用のuniform/attribute準備とGPUの遅延作業が残った。使用中のThree.js実装とCPU profileを照合し、prepareBattleで診断を維持したままgetUniformsを完了させ、種類ごとに代表1個を64×64で描画。GPU fenceを非同期に待ち、種類間はイベント処理へ戻る。gl.finishによる一括待機は行わない。
- 表示数・可視状態・カリング・viewport/scissorはfinallyで戻す。World、判定、アニメーション状態、実セーブは編集しない。既存のキャンセル・60秒期限を維持する。

## 実通信・描画の最終検査

`scripts/check-coop-live.mjs`。実ローカルWorker8793、独立した4つのChrome process、空profile、844×390、Intel Iris Xe/D3D11。同一PCのGPUを4画面で共有する試験であり、実スマホの性能ではない。通常生存、合法rifle/smg、pilotによる移動・射撃・装填、通常の強化選択。fixture API・World値の上書きは不使用。全体UI・音声・実セーブは別検査。

## 途中結果・負担・残件

- 最初のharnessは必須damage DOMが欠けて例外を出したため無効として別保存。DOM修正後にも6秒停止が残った。
- 色の事前確保だけでは約3.8〜4.5秒の停止が残り、煙素材を追加しても約2.9〜3.2秒。uniform初期化追加後は長いgetProgramInfoLogが消えたが、テクスチャ部分転送のgetParameterで約3秒のGPU待ちが残った。段階ごとの原本を保持した。
- 全種類を1回で描画する初版は準備自体の状態復元検査に成功したが、その後の全員ready待ち90秒で失敗。失敗時の各接続状態は保存しておらず、切断原因の確定とは扱わない。一度の大きい描画を避け、種類間でイベント処理へ戻す最終版で準備・出撃・60秒戦闘が成功した。
- 4画面同時の初回準備は41.3〜42.7秒。修正前の通常試行18.0〜20.2秒から増えた。必要な初回作業を戦闘前へ移す変更で、全体の計算量や起動時間を削減したという主張ではない。1台の実スマホでの準備時間・期限・復帰は未確認。
- この試行では入力ack最大約1秒と受信間隔最大約0.38秒が残った。その後phaseを読み戻すと、遅れは戦闘中の約12〜14秒へ集中し、選択停止/再開猶予による値ではなかった。追加の4画面同時試行では最大約4.7秒、1画面＋4人通信では最大約0.10秒となり、同一PC負荷・seed/密度等を分けた検査が必要。[追加の切り分け](input-latency.md)。全症状の完全解消、実インターネット/実スマホの快適化とは扱わない。
- 現行Three.jsのプログラム初期化と型に依存するため、ライブラリ更新時はこの実ブラウザ検査を再確認する。モデル簡略化は今回行っていない。

# 入力応答の遅れと、同一PCでの描画負荷の切り分け

2026-10-30。製品実装は `8d8c155`、開始HEADは `bf30da3`。この調査では製品コードを変更せず、`scripts/check-coop-live.mjs` に測定項目と診断条件を追加した。

## 確認できたこと

前回の `live-gpu-groups` 生データを読み戻すと、最大約1秒の入力応答は戦闘開始から約12〜14秒へ集中し、4人とも `combat` のままだった。強化選択の停止や再開猶予へ帰属させる根拠はない。新測定では、サーバーの受信済み番号 `inputAck` と、物理計算が適用した `Player.ack` のそれぞれに、送信番号・送信時刻・応答時刻を記録する。どちらも単なるpingではなく実際の移動・射撃・装填入力の応答である。

| 条件                             | 実時間→ゲーム時刻 | 適用応答p95 / 最大（4人の範囲） | 描画側frame p95 / 最大      |
| -------------------------------- | ----------------- | ------------------------------- | --------------------------- |
| 同一PCで4画面を描画、4人通常戦闘 | 45秒→40.0秒       | 2.39〜2.91秒 / 4.38〜4.67秒     | 33.5〜33.6ms / 200〜234ms   |
| 描画を外した4人通信診断          | 30秒→29.8秒       | 78.8〜80.5ms / 88.9〜102.3ms    | 描画検査ではない            |
| 1画面を実描画、ほか3人は通信診断 | 30秒→29.8秒       | 80.7〜82.1ms / 94.7〜98.6ms     | 描画client: 16.9ms / 50.0ms |

4画面試行では、受信確認応答も適用応答とほぼ同じ約4秒の遅れになった。物理計算を受理した後だけ長く待つ条件ではない。描画なしと1画面の試行では同じ遅れを再現せず、4人通信そのものだけで常時発生する遅れとは確認できない。同一PCの資源競合が関係する可能性はあるが、各回のseed・敵密度も異なるためGPUだけを原因と断定しない。4画面試行中には同じPCで読み取り調査も行った。

1画面試行の実描画準備は13.7秒、状態復元検査成功。4画面同時の約43秒を1台のスマホの準備時間とみなさない。1画面clientの同一ホスト時計から見たsnapshot年齢は中央値4ms、p95 16ms、最大29ms。実インターネットの時計同期や遅延の証明ではない。

すべて無効入力・画面例外・WebGLエラー・切断0、射撃・装填と撃破を確認。ただし4画面条件の遅延は未解消であり、機能検査の `passed:true` を快適さの合格へ読み替えない。前回の良好な1回だけで全症状解消とは扱わない。

## 再現と証拠

実ローカルWorkerを `wrangler.test.jsonc` / 8793で起動し、`scripts/check-coop-live.mjs` を実行する。既定は従来どおり4画面描画。`SWARM_LIVE_NETWORK_TIMING=1` で応答詳細を採取する。診断専用に `SWARM_LIVE_RENDER=0` で描画/準備を外すか、`SWARM_LIVE_RENDER_CLIENTS=1` で1画面だけ描画する。後者でも通常4人の権威計算・実WebSocket・合法pilot入力は維持する。描画を外したclientの空画像を実UIの合格証拠にはしない。

[集計JSON](input-latency-results.json) にソースhash・各条件・各clientの数値を保存。原本は `dist-validation/coop-comfort-20261030/live-ack-timing/`、`live-ack-no-render/`、`live-ack-one-render/`。受信確認の細分は現在の小さい単一stateメッセージを対象とし、分割state・再接続をこの測定だけで覆ったとはしない。試行ごとに対象ソースが不変だったことを照合した。

この後、実WebSocketへ遅延・帯域制限を加え、古い戦況の滞留を確認して送信制御を追加した。[改善と再検証](state-flow.md)を参照。実スマホ/実回線は未確認、独立レビューは未実施。外部保存は本人の「許可と承認します」を受け、下書きPR231へ保存した。merge・本番反映は今回の追加承認には含めない。

## 圧縮の前提

現行互換日付は2026-09-01。[Cloudflare公式の互換性資料](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#websocket-compression)では2023-08-15以降にWebSocket圧縮を既定有効とする。実ローカルWorkerへ圧縮を提示した接続でも `permessage-deflate; client_max_window_bits=15` の成立を確認した。[実測JSON](websocket-compression-results.json)、[再現script](websocket-compression-check.mjs)。古い検査部屋への最初の接続は410で、新しいローカル部屋を作って再確認した。実公開Workerの接続確認ではない。

そのため、新たに通信圧縮を追加したとはしない。制限helperは検査条件を明確にするため両側の圧縮を無効化し、接続ごと・方向ごとのpayload bytesで転送を制限する。HTTP、handshake、ping/pong等のcontrol frameは制限対象外。この値を、圧縮済みの実回線帯域と同一視しない。

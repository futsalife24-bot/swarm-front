## 確認した事実

先行45秒の大きなRAF間隔は全員39.4秒付近。一方、猶予外の入力送信空白は21秒/30秒付近で、同一事象ではなかった。41.4秒付近の全員の空白は強化選択からの復帰区間で、戦闘中の空白へ混ぜない。

先行client3は受信ACK352の時点（21421ms）で、送信済み・受信未確認が8件。その後ACK355（21653ms）で5件、ACK360（21766ms）で0件となり、窓4では途中に新しい入力を送れず、21395→21807msに412ms空いた。検査の`sample.unacked=11`はWorld適用ACK待ちであり、製品の受信ACK待ち8件と混同しない。急な窓縮小が入力を止める経路は確認できるが、これだけで上り帯域とサーバー処理待ちを識別できるわけではない。

`check-coop-live.mjs`へ入力受信時刻・最小遅れとの差・窓の前後・getError所要時間を追加した。実際の送受信を置き換えず、元のacknowledgeへ渡した後の値を読む。GPU確認は従来の毎秒`interval`と、計測終了後の`end`を選択可能にした。終了時は両方式ともGLエラーを確認する。計測区間外のGPU待ちを戦闘時間へ含めない。

全試行は同じゲーム実装で、source hash前後一致、接続/画面/GLエラー0。移動・射撃・装填の機能条件は通ったが、入力継続条件は満たしていない。原本の`passed=true`は機能検査であり、本記録の`inputContinuityPass`と分ける。死亡後はack=0の集計から除外する。低帯域試行の解除は送信意図から受信確認までで、人物の見た目の反応時間ではない。

各試行の部屋seed・ホスト負荷・回線条件は一致していない。この表からGPU確認を外したことによる悪化率や性能改善率を算出しない。1台で4ブラウザとWorkerを共有する条件も、実スマホ4台と別サーバーの条件へ読み替えない。

## 数値変更を採用しなかった理由

通常負荷側の追試は、約30秒に最小遅れとの差159〜203msで16→4へ縮み、約1秒後に16へ復帰した。しかし、その試行で唯一の猶予外ack=0は別の時刻（client2・10078ms）で窓16、差304msのまま発生した。窓縮小だけが残件の原因ではない。

GPU確認を終了時へ移した4画面条件では、差のp95が620〜716ms、最大805〜1081ms。上り1000B/s条件はp95が395〜534ms、最大1217〜2068msで、分布が重なる。単純な閾値だけで「普通の端末/サーバー待ち」と「細い上り」を正しく区別できるという証拠はない。

実装補助担当（呼出指定GPT-6.1 Sol/high、実行値未確認）にも原本を読み取り照合させた。これは独立監査の合格ではない。

- 採用: 受信ACKと適用ACKの区別、GPU確認の所要時間と受信時刻系列の追加、低帯域との比較。誤った原因への修正を避けるため。
- 保留: 中程度を8件、強い滞留を4件にする案。縮小直後の余裕は増えるが、低帯域で古い操作が溜まるリスクがある。今回の分布だけで境界を決めない。
- 不採用: 2回を3回にするだけ、閾値だけを引き上げるだけ、少しずつ縮小するだけで解決扱いする案。正常側の山が約0.7〜0.8秒続く例があり、低帯域の排水を遅らせ得る。実装・解消確認済みとは記さない。

現行4/16件、送信20Hz・受信35件/秒・入力期限250msを維持。ゲーム側へ推測の数値変更は入れない。実スマホの負荷と実回線の症状を照合して、入力窓、描画負荷、サーバー処理のどれを次に変更するかを決める。

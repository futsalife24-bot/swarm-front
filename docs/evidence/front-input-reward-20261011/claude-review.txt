レビュー結果：必須の修正なし。この2修正は監査へ渡して問題ありません

差分・単体テスト・ブラウザ検証スクリプトを読み、①②とも前回の提案どおりで、退行や二重付与の経路は見つかりませんでした。以下は監査資料の精度を上げるための非必須事項です。

① 未送信入力の破棄：問題なし
呼び出し位置：discardPendingInput() を clearInput() 1か所に置いたので、停止・非表示・blur・選択・phase変化・設定から戻る時・pagehide のすべてを同じ経路でカバーしています。
leave() との順序：leave() では network=null の後に clearInput が走るので、破棄は何もしませんが、接続は閉じるため問題ありません。
単体テストの範囲：3件で「短押しの保持」「破棄後の新しいタップは送信」「50ms間隔とack待ち4件を維持」の3点を押さえています。
実機の対照実験：修正前は送信・回避ともtrue、修正後は両方false、停止なしの対照は両方true。修正が効いていることを示すのに十分です。
中立パケット不要の判断：妥当です。ただし Worker の 250ms 失効はこちらでは未読なので、検証済みとして扱っているのはそちらの観測に基づく範囲です。

非必須（監査資料の補強）

check-front-input-resume.mjs の停止中2秒観測で、inputProbe.sent が空であることも assert してください。これで「中立パケットではなく失効で止まった」ことがスクリプト単体で証明できます。
同じ2秒観測は、敵の接触でノックバックされると誤って失敗する可能性があります（見逃しではなく誤検出の方向）。不安定に失敗したらこれを疑ってください。
front-network.ts を変更したので、実Worker の front-network.integration.ts を再実行したか、未実施かを監査資料に明記しておくと親切です。通常の送信内容は変わっていないので、リスクは低いです。
② 報酬表示：問題なし
成功側だけを保持して再試行：!status.progress の判定は「功績 +0」も成功として扱うので、日替わりの正当な0は再試行されません。
一部成功の両方向・pending消去の失敗・他の作戦の保留分：テストの期待値（37、57）を手で追い、保存処理の順序と一致することを確認しました。

ゲーム内時間：結果画面では world.time が止まっているので、再試行のたびに表示額が変わることはありません。

非必須（仕様として監査資料に一言書いておく事項）

再読込後の表示：再読込後は「攻略コイン +30」と表示されますが、これは「今回新たに加算した額」ではなく「この作戦で獲得した額」です。重複判定で実際の加算は0なので正しい挙動ですが、意味の違いを明記してください。
再読込時の pending 書き込み：再読込のたびに pending キーへ一度書き込みが発生します（最終的には "[]"）。変更前と同じ挙動なので退行ではありません。
時計が巻き戻った場合：receipt.at <= receiptFloor になると「功績 受取済み」と表示されます。変更前は「+0」だったので悪化ではありません。
テスト名：「防衛戦では…」というテストの実際の入力は daily です。コード上は同じ経路（campaignSeconds=null）ですが、名前を「日替わり」に直すか、defense のケースを1件足すと監査で指摘されずに済みます。
実Chromeの証拠：記録が「credits20一回分」だけです。生存戦で60秒以上経っていた場合はコイン額も確認できるはずなので、もし確認していれば数値を証拠に加えてください。

記録のみ（今回の範囲外・推測）

Worker の 250ms 失効と、クライアントの「ack待ち4件・50ms間隔」の組み合わせについてです。往復遅延がおおむね400ms以上になると、送信の待ち時間が失効時間を超え、移動が途切れる可能性があります。ただし、サーバーがどの頻度で state を送るかに依存するため、未検証の推測です。今回の修正では変更しない現状どおりの挙動なので、必要になれば次回の調査候補にしてください。

Swarm Front 共同調査（base a478059）

結論を先に述べます。修正を提案するのは①と②の2件です。どちらもクライアント側の小さな変更で済み、保存形式・通信形式・バランス数値は変えません。③は「楽しさを損なう不整合」と確定できるものがソース内に見当たらないため、数値は据え置きとし、対象ソース外の確認事項を2件挙げます。

凡例：確定＝コード読解または添付の単体観測で成立／仮説＝成立条件は読めるが影響は未測定／推測＝対象ソース外の動作に依存

1. 【P1・確定】停止・選択・非表示をまたいで未送信入力が残る

根拠

front-network.ts:368-390：送信を見送ったとき、reload/swap/dodge/jump は pendingInput に OR で蓄積されます。この値がクリアされるのは送信成功時（389行）と connect() 時（157行）だけです。
front-app.ts:159-165：clearInput() は Controls・accumulator・previous しかリセットしません。
front-app.ts:1163：network.input() は active の間しか呼ばれないので、非アクティブ中は pending がそのまま保持されます。
添付の pending-input-result.json で、再開後の中立入力に dodge と reload が混入することを確認済みです（通信クラス単体での観測）。

発生条件（コードから導出。実画面では未再現）

送信が見送られる条件は3つあります。
前回送信から50ms未満（381行）
bufferedAmount>4096（382行）
未ack が4件以上（383行）
3つ目は、送信間隔が50msなので往復遅延がおおむね200msを超えると成立します。つまり送信バッファの混雑だけでなく、モバイル回線の高遅延でも発生し得ます。サーバーのack頻度は対象外のため推測です。
この状態で dodge/reload をタップした直後に、Esc・blur・非表示・強化選択・phase変化のいずれかで clearInput が走ると、再開後の最初の送信で回避や装填が勝手に発動します。

影響：再開直後の意図しない回避（残像地雷・戦術装填・緊急装甲の誤発動を含む）、装填の誤発動、ジャンプの誤発動。

最小対処


ts
// front-network.ts（FrontNetworkに追加）
/** 停止・選択・非表示で未送信入力だけ破棄。inputAt・inFlightInputs・ack追跡は維持。 */
discardPendingInput() { this.pendingInput = undefined; }

// front-app.ts clearInput() 内に追加
network?.discardPendingInput();
短押し保持は残ります。 アクティブ中の50ms間引きでの OR 保持は変更しません。
ソロと挙動が揃います。 ソロでは controls.reset() によって停止前のタップが同じように消えます。
seq の欠番は既存動作の範囲内です。 371行で毎フレーム最新の seq に上書きしているため、通常運用でも送られない seq は既に発生しています。ただし Controls の seq 採番は対象外なので、ここは推測です。

検証条件

単体（既存の偽Socketを流用）。以下の4点を確認します。
(a) 混雑中に dodge/reload を押す → discard → 混雑解除 → 中立入力：送信内容が false になる
(b) discard を呼ばない場合：タップが次の送信に残る（短押し保持の回帰確認）
(c) 未ack 4件で詰まっている間に discard：inFlightInputs の件数は変わらず、ack を受けると送信が再開する
(d) inputAt が変わらず、50ms間隔が維持される
実通信：実Worker と実際の FrontNetwork を使い、bufferedAmount を一時的に固定するか、CDP の upload throttling で詰まらせます。「タップ → Esc → 解除 → 再開」の後、サーバー state でプレイヤーの回避が始まらないことを確認します。対照として、停止を挟まない場合は回避が1回だけ適用されることも確認します。
実画面：1人協力部屋で、強化選択に入る直前のタップと、選択して再開した後の挙動を同じ手順で確認します。
2. 【P2・確定】戦果保存の一部成功後、再試行で表示が+0になる（両方向とも）

根拠

再試行ボタンは front-app.ts:1024-1029 で awardedRun="" に戻し、1177-1203行の処理全体をやり直します。
ケースA：功績は保存できたがコインが失敗した場合
再試行すると front-progress.ts:145-146 の重複判定で reward:0, saved:true が返り、表示は「功績 +0 · 攻略コイン +30」になります。
ケースB：功績が失敗しコインは成功した場合
1200-1202行は result.saved=false のとき campaignText を捨てるため、初回はコイン付与が表示されません。
再試行すると、front-campaign.ts:170-176 で pending に再登録され、awardFrontCampaign の receipt 判定（121行）で0が返ります。表示は「功績 +100 · 攻略コイン +0」になります。
二重付与は両ケースとも起きません。各保存先の receipt で防がれていることをコード上で確認しました。

影響：受け取った報酬が失われたように見えます。

最小対処（表示側のみ。保存形式と二重付与防止は変えない）

run ごとにメモリ上で {progress, coins} の成功値を持ち、まだ成功していない側だけを再試行します。
功績の額は、戻り値の progress.receipts.find(r => r.id === run)?.reward から取ります。重複判定の経路でも初回の額が残っているので、ページを再読込した後の結果再接続でも正しく表示できます。
功績が失敗した場合でもコイン側の結果を表示します。1200行の分岐を「功績」「コイン」それぞれ独立に組み立てる形に直します。
補足（低優先度）：queueFrontCampaignReward の戻り値は、他の run の未保存分も合算します（152-161行）。正確に表示するなら、コイン額の計算式を関数として共有する案がありますが、今回は見送りで構いません。

検証条件

判定部分を純関数として切り出し、偽Storage で次の3パターンを確認します。
(A) 1回目：功績のみ成功 → 2回目：両方成功
(B) 1回目：コインのみ成功 → 2回目：両方成功
(C) 1回目：両方失敗 → 2回目：両方成功
各パターンで、表示が初回の額のまま変わらないことと、保存後の credits と coins が1回分だけ増えていることを確認します。連打しても増えないことも確認します。
T6 保存ブラウザ試験に、特定キーの setItem だけを失敗させる1ケースを追加します。
3. 【要確認・推測】停止中の協力プレイヤーにサーバーが最後の入力を適用し続けるか

根拠：協力プレイの停止中は「部隊の戦闘は続きます」（front-app.ts:912）。しかし clearInput は中立入力を送らず、停止後は何も送信しません（1163行）。サーバーの入力保持方式は対象ソース外です。

影響（もしサーバーが最後の入力を保持する場合）：停止中も移動や射撃が続きます。①より体験への影響が大きい可能性があります。

検証：実Worker で W を押したまま Esc を押し、2秒間サーバー state の座標が動き続けるかを見ます。動く場合だけ、clearInput 時に中立入力を1回送る対処を別途検討します。その場合も、ack上限と50ms間隔を迂回しない送り方にする必要があります。

4. 【要確認・推測】融合後の実効段階が素材の上限を超える

根拠：front-upgrades.ts:155-167 の frontEffectiveLevels は、素材の段階を「上限＋融合段階」に設定します。たとえば導火は最大6、装甲補強は最大7になります。front-run.ts:268-303 の HP・弾倉・装填は線形計算なので問題ありません。一方、front-combat.ts の各効果がこれらの値をどう扱うかは対象ソース外です。

影響（推測）：効果を表引きで実装している場合、範囲外の参照で NaN や効果なしになるおそれがあります。逆に線形で青天井なら、「緊急装甲10%×6」や「回避促進8%×6」が支配的な組み合わせになる可能性があります。どちらになるかは判断できません。

検証：front-combat.ts 内の levels[...] の参照箇所をすべて洗い出します。そのうえで融合9種について、融合段階1〜3の効果値が素材上限以上かつ有限であることを単体試験で確認します。数値の調整は、この結果を見てから別途判断します。

5. 【P3・仮説】協力時、複数の未選択取得権が1つの15秒期限を共有する

根拠

防衛戦と日替わりの345秒補給（front-run.ts:404-417）は全経験値を強制回収するため、閾値を複数越えることがあります。
1つ選ぶと次の候補が開きますが（359行）、selectionDeadline は延長されません。
期限が切れると、残りは既定カードで自動確定します（578-599行）。

影響（仮説）：2枚目以降をじっくり選べず、自動選択になることがあります。

対処：今回は変更しません。期限を延長すると他の隊員の待ち時間が増えるためです。実通信の2人試験で、345秒時点の未選択取得権の件数と自動確定の発生だけを記録し、実際に問題になるかを判断材料にします。

検討したが据え置くもの（反例）
開幕3択がすべて汎用カードになり得る：combinationsFor は候補プール内の全組み合わせから抽選するため起こり得ます。ただし利用者が6種以上を自分で選んだ結果なので、仕様として維持します。
融合の保証枠（576行）：素材が揃った後、融合カードが毎回提示されて既定選択にもなります。これは意図された誘導で、旧版の保証と同じ構造です。
協力人数補正：出現間隔と上限は人数に依存しません（466-469行）。経験値は全員で共有し、取得権も全員に同数付与されます（390-403行）。world.scale と spawn() は対象ソース外のため、人数による難易度差は判断できません。BALANCE-T7 の bot 成績もここには換算しません。
生存戦の功績：60秒以降に帰還すれば勝利扱いで100、長時間生存しても全滅なら敗北扱いで20です（front-progress.ts:156-162、front-run.ts:534-545）。功績と勝利数の使い道が対象ソースから読めないため、仮説として記録するに留めます。
再抽選が作戦全体で2回：仕様の範囲内として変更しません。

Codexへの依頼順：①を実装し、単体・実通信・実画面で検証 → ③の確認（ここで①に追加の対処が要るかが決まります）→ ②を実装 → ④を読解して単体試験。⑤は計測のみ。バランス値・依存・保存形式は変更なし。

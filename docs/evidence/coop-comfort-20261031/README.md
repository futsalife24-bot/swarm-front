## 確認できた別の不具合と変更

- 分割戦況の組立期限は2秒。失敗してACKを返せない状態が2回続くと、サーバーの未確認2枠が埋まり続ける。ping/pongは届くため既存の無通信監視も働かず、戦況だけ永久停止する経路を再現した。変更前の合成輸送検査では60秒で戦況0・ACK0、600回の更新が保留。動画は時刻が進むため、この現象が動画の原因だという証拠はない。
- 分割破損・期限切れを正常な受信途中と区別し、接続を閉じて通常の再接続へ進める。期限タイマーは組立中だけ。正常なロビー待機は切断しない。同じ復帰トークンを用い、保存形式・戦闘ルールは変更しない。
- 再接続の試行回数は正常な戦況またはロビーが届いてからリセットする。welcomeだけ届く壊れた接続の無限再試行を防ぐ。故意退出・fatal・新接続では旧タイマーを回収する。
- 実Worker検査でcloseへの応答待ちも発見。RoomのwebSocketCloseで明示応答し、失敗時も部屋の後処理を行う。製品とテストのcompatibility_dateは2026-09で公式上は自動応答の対象だが、手元ランタイムでは明示応答前に1006と約10秒の余分な待ちを観測した。原因を互換日付の古さとは断定しない。[Cloudflare公式の切断応答仕様](https://developers.cloudflare.com/durable-objects/api/base/#websocketclose)では、自動応答後のclose呼出しも安全な無操作とされる。
- 協力戦の左下に「往復○ms・更新○/s」を追加。既存ping/pongの実経過と受理した戦況の直近1秒の件数を使う。新しい通信・外部集計・永続保存は増やさない。FPSから通信品質を推測しない。再接続時に計測をリセットし、欠測は「—」、1秒超の戦況停止は待ち時間を示す。

実機の遅延が664msだとは扱わない。今回の継続検査のpassedは手順・データ取得の成功であり、快適さの合格ではない。前回の短い歩き始め検査の数値を継続操作へ一般化しない。予測の先行距離を広げたり未確認送信枠を無制限に増やしたりすると、命中との不一致や古いデータの滞留を悪化させ得るため、今回は変更していない。

### 監査結果

- `manifest.json` 記載の **113ファイルすべてSHA256一致**。`change.diff` はCRLFだったためLF正規化後に対象ツリーへ逆適用確認し、**対象SHAの実ソースと差分が一致**しました。
- 製品変更は `game.ts` の `enemySpawnHeight()` 抽出と `foundry-spawning.ts` の洞窟増援への共通適用に限定。通常spawnの式自体は同値です。
- 洞窟では候補判定・最終配置とも同じ高度式になり、hornetの **上限5** が保持されています。
- `spawnPoint()` の半径は `enemyOrdinal` から算出する次の実spawn個体サイズと一致。候補探索中はordinalを消費しないためズレません。
- 独立再計算では、修正前は**実個体半径基準で12/1,260個体が洞窟形状違反**していましたが、修正後は **0/1,260**。元資料が基本半径で拾った2件だけでなく、大型個体分まで解消しています。
- 草原・雪峡の観測 **4,292件は修正前後で完全一致**。洞窟側で変化した243配置も、差分は位置だけで、kind・seed・route等は維持。抽選ロジックの `random(w)` 呼出数も不変です。
- `kinds.shift()`、保留キュー、敵上限、生成数、同時部位破壊処理には製品差分なし。既存の128破壊パターン、同tick頭部/胴体、40体上限テストとも整合します。
- `game.ts ↔ foundry-spawning.ts` の循環importは元から存在。今回追加されたbindingはトップレベルで参照されず、初期化時TDZを踏む経路は確認できません。Worker用tsconfigにもsharedが含まれています。
- 同梱の型チェック、857テスト、Vite build、Worker production dry-run、2 socket通信結果は内容を照合済み。ただしこれは実装側証拠であり、監査側実行の代用にはしていません。

### 任意指摘

洞窟ST10/ST16で**実Worker上のworm頭部撃破 → 増援生成まで**を1本E2E化できると、今回唯一大きく残る境界が閉じます。ただしsharedロジック、Worker bundling、通信形式に不整合は見つからず、**公開阻止事項にはしません**。

### 監査側の検証限界

監査環境では依存取得が完了せず、Vitest/Vite/Wranglerの独立再実行はできませんでした。代わりにmanifest検証、diff逆適用、ソース経路照合、修正前後観測の独立計算、証拠画像確認を実施しています。実機タッチ、長期負荷、全seed/全敵モデル、全作戦完走、洞窟Worker実撃破映像は未確認です。

**結論：対象SHA `672bc9c63a7558f39db347bdf1901ed5d4bc0d8f` は公開前監査として合格です。**

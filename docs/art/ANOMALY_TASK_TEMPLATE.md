## A. 個体設計票（候補ごとにコピーして記入）

記録先の例：`assets/blender/candidates/<既存ID>/<候補版>/DESIGN.md`。山括弧は実際のID・版へ置換する。

|項目|記入欄|
|---|---|
|状態|提案 / 制作中 / 自己検証済み / ユーザー見た目承認済み（根拠を付記）|
|対象|既存ID、形態、現行表示名、採用GLBとSHA-256、branch・開始HEAD|
|維持する性能|HP・人数/ステージ補正、速度、高度、移動方式、射程、ダメージ、弾速/重力、発射数、判定形状/半径、発射原点・方向、wind/impact/cooldown、標的選択、wave・報酬。対象コードの位置と値を転記|
|仮の新名称|人類の観察に基づく命名理由。名称は提案であり表示名の変更・承認を意味しない|
|模倣対象|似ている形または機能。断定と観察を分ける|
|不完全さ|主役となる異常1〜2点、形・機能・動きのどこで伝えるか|
|体の構成|主な塊、姿勢、輪郭、支持部、前後・攻撃方向、ゲーム内寸法|
|素材|本体素材、被覆の有無と種類、付着物、環境擬態の有無、乾いた見せ方|
|攻撃|身体構造・攻撃器官と能力の関係、予備動作、実発射位置/時刻との対応|
|差別化|比較する既存敵、輪郭・姿勢・動きの差、共通の素材表現・整理度|
|変更しない仕様|性能・移動・判定・発射位置/時刻・AI・通信等を具体的に列記|
|動作対応表|待機/移動/攻撃/被弾/撃破/必要な特殊行動 → 現行状態 → クリップまたは既存演出 → 時刻/ループ/接地条件|
|予算|現行実測、候補上限（暫定なら明記）、差、根拠、測定方法|

|提案上の仮定|未指定形状・素材・仮称など、規約内で制作側が提案した事項|

細部ごとの質問を増やさず、規約内の未指定造形は提案する。重要な不明点と仮定を分離する。提案した名称・形をユーザー承認済みと記録しない。仕様変更が必要なら候補制作から分離し、既存の承認境界に従う。

## B. 大きな形から作る

1. 現行モデルと同じ比較条件で、簡易モデルの塊・輪郭・体格・姿勢・攻撃方向を確認する。単色表示とゲーム表示サイズを含める。
2. 模倣対象と不完全さが読み取れること、他種との輪郭差、役割の読みやすさを確認してから、素材・被覆・付着物・細部へ進む。弱い輪郭を装飾で隠さない。
3. 必要な支持構造と器官に合わせてリグ・動作を作る。既存生成器の部位タグ付け、材質単位の結合、剛体ウェイト、NLAクリップ書出しを参考にする。別種へHOUNDの五脚や20骨を一律に強制しない。
4. 被覆の変形・貫通、折り畳みの支持関係を動作中にも確認する。意図した異常と不具合を区別する。

## C. 再生成と候補の隔離

候補一式は `assets/blender/candidates/<ID>/<版>/` に、`DESIGN.md`、生成器と必要な補助コード、形状パラメータ、`.blend`、GLB、使用素材/出典/利用条件、seed（不要ならなし）、検証ログ、静止画/動画をまとめる。既存採用ファイルを上書きしない。変更指示では指定外の形状・素材・seedを固定し、変更パラメータの差を残す。

**既存生成器をそのまま再実行しない。** `phase1_common.setup()` は現在のシーンを全削除し、exportやmotion生成器は既存の `assets/blender/source/*`・`public/assets/enemies/*`・検証先へ固定出力する。motion生成器は静止生成器のコード断片を取り出して実行するため、依存ファイルとその版も必要。

候補用コピーで全保存先・検証先を候補フォルダへ変更し、`REPO` の `parents[3]` 等の位置依存、import先、参照静止生成器のパスを確認してから実行する。既存生成器本体は保護し、共通関数を再利用する範囲にとどめる。新しい制作基盤を丸ごと作らない。

専用の別Blenderプロセスでfactory-startupから実行し、作業中の別シーンへスクリプトを流さない。全選択削除・再importはこの専用プロセスだけで行う。候補はpublic配下へ置かず、通常ビルドの混入・採用URLへの書込みを防ぐ。

PowerShellでの実行形（候補スクリプトを準備した後。パスは実在確認して置換）：

```powershell
$blenderExe = '<確認したblender.exeの絶対パス>'
& $blenderExe --version
& $blenderExe --background --factory-startup --python-exit-code 1 --python 'assets/blender/candidates/<ID>/<版>/build_candidate.py'
```

過去記録の使用版はBlender 5.2.1（HOUND記録ではLTS表記）。今回インストール版は未確認であり、制作時は実行した `--version` 出力を正とする。コマンド、作業ディレクトリ、Blender版、生成器/依存/素材のハッシュ、パラメータ、seedを保存する。PRISM/RAY/FOUNDRYの既存motion生成器は `-- prism|ray|foundry_zero` で対象選択する方式。候補版でも1体だけを選び、実際に用いた引数を記録する。

## D. 現行ゲームとの契約（2026-09-10コード確認）

標準skinned GLBが採用形式。BlenderはZ-up / forward +Y、GLBはY-up / forward -Z、メートル・scale=1。原点は既存インスタンス変換の基準。地上支持部はY=0を基準とし、浮遊部・空中敵は原点からのクリアランスとゲーム側高度を分けて確認する。中立時だけでなく全動作でbounds・接地・原点・階層・正スケールを検査する。

`hound-motion.ts` は現在、次の**読込条件**を固定している。全種共通の造形規約や推奨骨格ではない。

|既存ID / アセット|SkinnedMesh数|骨数|GLBの必要クリップ|
|---|---:|---:|---|
|crawler / hound（ant・spiderも共有）|4|20|Idle / Locomotion / Lunge|
|spitter / prism|4|9|Idle / Locomotion / Attack|
|hornet / ray|4|15|Idle / Locomotion / Attack|
|boss通常形態 / foundry_zero|5|21|Idle / Locomotion / Attack|

loaderはAttackを内部名Lungeへ読み替え、メッシュ間のbindMatrixとmatrixWorldの一致も要求する。標準AnimationMixerで開けても、これらを満たさなければ現行ゲームでは拒否される。独自骨格の候補は標準GLBで検証し、現行条件との差と必要な描画側対応を別項目へ記録する。骨数を見かけ上合わせるだけで採用可能としない。候補URLは既存loaderで指定できないため、制作時は候補専用の検証ページ/検証用アダプターで同じ再生経路を使う。正式URLの変更は別工程。

`structure-timing.ts` のimpact / durationはcrawler 0.45 / 1.2秒、spitter 0.8 / 1.6秒、hornet 2.05 / 3.6秒、通常boss 3.1 / 4.8秒。制作開始時に再確認する。antはwind 0.8秒をHOUNDのimpactへ再マップし、spiderもHOUND再生を共有するため、専用造形ではsharedの実行段階と描画対応を調べる。連結炉はこの通常boss表を流用しない。

移動はゲームの座標更新を唯一の移動元とし、GLBに累積root motionを入れない。現行の距離再生はHOUND系が0.72m/0.8秒、通常bossが0.48m/2秒、他は時間再生。身体の局所的な送りとワールド移動を区別し、足滑り・二重移動を測る。方向転換・ブレンド・停止・復帰も確認する。spiderはjump/perch/jumpFrom等の実状態に、離地・空中・着地・壁待機/離脱を対応付け、独立した跳躍をアニメーションで重ねない。

発射原点は骨ソケットから自動取得されると仮定しない。`game.ts` の弾生成座標と `render.ts` の個体変換を読んで、発射時刻の器官の世界座標・方向と実弾を比較する。見た目に合わせて弾の座標や判定を勝手に動かさない。

現行loaderの再生選択は3クリップ。待機・移動・攻撃以外の被弾/撃破等は、対象に必要なものを設計票で既存演出へ対応付ける。新規クリップを保存するだけでは再生されない。専用クリップが必要なら制作し、再生接続が追加実装か未対応かを明記する。撃破演出も造形正本の禁止表現に従う。

### 予算の決め方

全種共通のポリゴン上限は今回の調査範囲では見つかっていない。既存報告値はHOUND motion 5,128tri、RAY 7,838tri、FOUNDRY ZERO 18,680triであり、今回測定した値・新種の一律予算ではない。制作時に対象の実GLBを測り、三角形数、頂点数、材質/バッチ数、骨数、クリップ長、GLB bytes、画像テクスチャの解像度/容量、GPU行列テクスチャ容量を記録する。

未定義項目は「対象現行実測を当面の上限」とする暫定値を設計票へ記録し、増加が必要な場合は理由と同時表示負荷を比較する。骨数・メッシュ数の固定読込条件と性能予算を区別する。1体と現行の複数体条件（HOUNDの既存検証は1/10/40体）でdraw calls・表示数・CPU/GPU負荷を測る。SwiftShader、オフライン30fps動画、見た目だけでAndroid/iPhoneのFPS・発熱を保証しない。

## E. 書出した実物の検証

1. `.blend` 保存 → GLB書出し → 別読込を行い、有限座標、退化面、scale、階層、骨/メッシュ/材質/クリップ、boundsと形状を照合する。現行exportはY-up、選択物、NLA_TRACKS、sampling有効、カメラ/ライトなし。画像UVを出さない既存設定 `export_texcoords=False` は、毛皮・擬態等に画像を使う場合そのまま流用しない。glTF対応の材質・UV・必要なベイク/メッシュ表現へ変換し、出力先で実確認する。
2. 標準GLTFLoader/AnimationMixerと現行GPUスキニング経路を比較。実スキニング後の頂点を全クリップでサンプリングし、有限値・地面潜り・接地足の世界移動・ループ継ぎ目・攻撃器官と発射座標/時刻を検査する。意図したクリアランス・許容差・計測間隔を記録する。
3. 既存の `check_hound_motion.mjs` / `check_enemy_motion.mjs`、`check_enemy_phase1.mjs` の検査処理を対象1体へ再利用する。既存チェックは採用URL・出力先・複数種ループが固定されるものがあるため、候補用に入力URL・保存先・対象・期待値を明示してから実行する。既存モデルを検査した結果を候補の合格に転用しない。
4. 実読込処理または対応する候補検証環境で、形状・材質・動き・縮尺・接地を表示確認する。複数個体の位相、状態遷移/中断、cleanup、fallback、描画前後のWorld不変を影響範囲に応じて検査する。描画接続コードを変更した場合はtypecheck・関連テスト・buildと適用AGENTSの必須検証を実行する。候補だけなら無関係な全件E2Eを増やさない。
5. Blender固有の毛・シェーダー・変形・粒子等がGLBで再現しない場合、再現できる方法へ変更するか追加実装へ分離する。専用プレビューだけの効果をGLBやゲームで再現済みとしない。

## F. 比較証拠と完了判定

正面・側面・背面・斜めのPNG、単色輪郭、必要動作の動画または再生可能プレビュー、ゲーム表示サイズの画像を残す。同じ照明・カメラ・縮尺・解像度・同じ動作時刻で現行/候補/比較種を並べる。個別auto-fitで寸法差を隠さない。

既存 `preview-motion/`、`preview-enemy-motion/` と `record_hound_motion.mjs` / `record_enemy_motion.mjs` の回転・シーク・動画保存を再利用する際も、候補だけを読み、候補の証拠先へ保存する。動画は保存後に読み戻して複数時刻を再生/シークし、静止画も実際に開いて確認する。

報告は「自動数値検査」「画像を見て確認」「動画を再生して確認」「未確認・追加実装・ユーザー判断」を分ける。造形正本の合格チェックリストを証拠ファイルへ対応付け、自己採点だけで合格にしない。実機未測定は未測定と明記する。

最初の1体は**基準モデル候補**として提出する。ユーザーの見た目承認を得た後にだけ、造形正本の基準モデル欄へ対象版と証拠・承認記録を登録する。制作見本は品質と手順の見本であり、他種の骨格・装飾の強制ではない。候補制作の完了、見た目承認、正式差し替え、公開は別の状態として報告する。

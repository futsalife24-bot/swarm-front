## P0 — 救助バグ

### 味方が救助できない

ユーザーが最優先と明記。**仕様ではなくバグとして扱う。**

調査済みの事実（2026-09-06 / HEAD `59610da`）:

- 蘇生処理は実装されており、動いているように見える — `src/shared/game.ts:519-536`
  3.5m以内・視線が通る・`revive` 入力が2.5秒継続 → HP90で復帰
- ダウン時に `down = 25` を代入しているが、**この値をどこでも減算していない** — `src/shared/game.ts:315`
  つまり「時間切れで蘇生できなくなる」実装にはなっていない。STATE.mdの「作戦終了まで蘇生可能」と一致する
- 蘇生ボタンはレイアウト上つねに存在する — `src/client/layout.ts:7,16,39`。表示条件による出し分けは見つからなかった

**実機の症状（ユーザー確認 2026-09-06）: 蘇生ボタンを押しても画面に何も出ない。**

この症状から原因を特定した。**通信と権威処理は正常で、欠けているのは救助する側のフィードバック。**

確認した経路（すべて正常）:

- クライアントは押下中つねに `revive: true` を送る — `src/client/input.ts:138-140`（`refresh()` が押されているボタンを毎回反映）
- 送信は20Hz（0.05秒ごと）— `src/main.ts:658-662`。サーバーの入力有効期限250msに対し十分な頻度
- サーバーは `revive` を継続入力として保持する — `server/worker.ts:436-443`。
  ワンショット扱いでリセットされるのは `swap` / `dodge` / `reload` のみで、`revive` は含まれない

**欠陥1 — 救助する側に円形ゲージが存在しない。**
`updateCooldowns()` が円形ゲージ（`cooling` クラス＋`--remaining`）を作っているのは
**`dodge` と `reload` の2つだけ** — `src/client/hud.ts:7-10`。`revive` はこのループに入っていない。
つまり蘇生ボタンは、押しても見た目が一切変化しない唯一のボタンになっている。

**欠陥2 — 蘇生の進捗が、倒れている本人にしか表示されない。**
進捗バーを描いているのは `p.hp <= 0` の分岐の中 — `src/client/hud.ts:95-101`。
`p` は自分自身なので、**救助している側の画面には進捗が出ない**。
救助側は「距離が足りないのか」「遮蔽で視線が通っていないのか」「そもそも効いているのか」を判別できない。

**寄与する要因** — 倒れた味方の位置を示すマーカーが無い（→ P1）。加えて蘇生ボタンは
救助対象がいない時も同じ見た目で常時表示されるため、「押しても無反応」と区別がつかない。

### 修正方針

1. `updateCooldowns()` に `revive` を追加し、進行中は円形ゲージを回す
2. 救助側のHUDにも進捗と対象を表示する。対象の状態を3つに描き分ける:
   - 範囲外 → 距離を出す
   - 範囲内だが視線が通らない → 遮蔽物ありを明示
   - 範囲内かつ視線あり → 進捗ゲージ
3. 救助対象がいない時は蘇生ボタンを無効の見た目にする
4. 上記が入ってからもう一度実機で確認する。**それでも蘇生できない場合のみ**、
   `visible()` の高さ1.2m判定（`src/shared/game.ts:271-280`）を疑う。
   現時点でこれを先に触るのは根拠がない

## P1 — 「どこに誰がいるか分からない」の解消

3つの別機能に見えるが、**現れる症状は1つ**。まとめて扱うのが最も安い。
P0の仮説3が当たりだった場合、ここがそのまま修正になる。

この順で進める:

1. **ユーザー名の登録場所** — 名前がないと以下2つが「誰なのか分からない表示」になるため最初
2. **味方の頭上に簡易HPゲージ** — ダウン中は別マーカーにすると、救助の動線がそのまま繋がる
3. **ミニマップ** — 敵と味方の位置。ユーザーが「必須。敵の位置が分からないと難易度が理不尽になる」と明記

## P3 — 敵のバリエーション

現状は雑魚2種類。ここを厚くすると作品の density が上がる。**実装コストの安い順**:

1. **蟻型** — 噛みつき＋酸の散弾。既存の地上敵の枠に収まる。最も安い
2. **蜘蛛型の壁張り付き** — ジャンプ移動、ビル等の壁面に貼り付く。既存敵の挙動拡張。中
3. **蜂型** — 空中飛来・針・壁に止まる。**空中敵は新しい概念**で、当たり判定・照準・ミニマップ表記が
   まとめて増える。最も高い

## 要仕様確定 — 位置ゲー機能

ユーザーの構想（2026-09-06 時点、口頭）:

- マップを**ブロックに分割**する
- ブロックから**装備素材**や**特殊ボスステージ**を入手する
- 入手したものは**協力プレイで共有・配布**できる

**確定（2026-09-06・ユーザー判断）: 「位置」は現実のGPS位置。** ゲーム内マップの区画ではない。

この決定により、以下が本作の新しい前提として発生する。**どれも今の実装には存在しない。**

- **位置情報の利用許可** — ブラウザの Geolocation 許可。拒否された場合も遊べる形にする必要がある
- **プライバシー方針** — 現実の居場所を扱う。協力プレイで「共有配布」する以上、
  友人に自分の生活圏が推測される可能性がある。何を他人に見せ、何を見せないかを先に決める
- **位置偽装への耐性** — ブラウザのGeolocationは偽装が容易。STATE.mdに「完全な改ざん防止は未実装」と
  明記されている現状と正面から衝突する。**PvPではなく友人との協力なので実害は小さいが、
  「偽装すれば最上位素材が取り放題」になる設計は避ける**
- **サーバー側の永続化** — ブロックの取得状況は端末保存では足りない。Durable Objects の構成と
  無料枠の使用量に影響する

着手前になお確定が必要な点:

1. **ブロックの大きさ** — 数十mか、数百mか、市区町村単位か。生活圏だけで遊べるのか、
   出かけないと進まないのかがここで決まる
2. **ブロックの状態は誰のものか** — 個人ごとか、部隊で共有か、全プレイヤー共有の陣取りか
3. **「共有配布」の意味** — 手持ちの素材を渡すのか、入手時に部隊全員へ同時付与されるのか。
   前者はクラウドセーブと改ざん防止に踏み込む
4. **特殊ボスステージの出現条件** — 特定ブロックに固定なのか、条件を満たすと湧くのか

**この機能は単独で作品の規模を一段上げる。** P0〜P2が片付き、実機で安定して遊べるように
なってから設計に入る。現時点では要件の記録にとどめる。
